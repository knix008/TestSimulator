# MyEBookReader — 구조 설명

하나의 화면 코드로 **웹 브라우저와 데스크톱(Electron)** 을 모두 지원하는 전자책 리더입니다.
이 문서는 코드가 어떻게 나뉘어 있고, 왜 그렇게 되어 있는지를 설명합니다.

## 2. 통일된 책 인터페이스

형식마다 파일 구조가 전혀 다르지만, 화면은 한 가지 모양만 알면 되도록
`lib/book.js` 가 모든 해석기를 같은 모양으로 감쌉니다.

```js
{
  format, formatLabel, reflowable,     // 'epub' · 'EPUB' · true
  meta,                                 // 제목 · 지은이 · 펴낸곳 · 언어 …
  sections, sectionCount,               // 장(또는 쪽) 목록
  toc,                                  // 목차 트리 [{ label, section, anchor, children }]
  loadSection(i),                       // { kind: 'html'|'image'|'pdf', html, src, page … }
  readSectionText(i),                   // 검색 · 내보내기용 평문
  resourceUrl(path), cover(), destroy()
}
```

* **reflowable** (EPUB · MOBI · FB2 · MD · HTML · TXT) — 정화된 HTML을 본문 폭·글꼴
  설정에 맞춰 흘려 보여 줍니다. 한 쪽씩 보기는 CSS 단 나눔으로 구현합니다.

* **fixed** (PDF · DjVu · CBZ · 그림) — 쪽을 캔버스나 그림으로 그립니다. 확대·회전과
  **한 장/두 장씩(펼침)** 이 여기 적용되고, 펼침에서는 한 번에 두 쪽씩 넘어갑니다.

### 한 장을 끝까지 읽고, 뒤로도 읽기

장을 다 보기 전에 다음 장으로 넘어가지 않는 것과, 뒤로 넘겼을 때 앞 장의 **끝**에
도착하는 것은 둘 다 필요합니다. 앞 장의 맨 앞에 도착하면 이전 쪽을 한 번 더 누르는
순간 또 앞 장으로 가 버리고, 방금 도착한 장은 한 글자도 읽히지 않습니다. 그래서
`BookView.arriveAtEnd()` 가 있습니다 — 뒤로 넘기다 장을 벗어나는 App이 이것을 부르고,
새 장이 배치되는 순간(`useLayoutEffect`) 마지막 단 또는 본문 맨 아래로 내려갑니다.

단 수는 `columnPageCount()` 가 **올림**으로 셉니다. 2.4화면짜리 장을 반올림해 두 쪽이라
하면 마지막 5분의 2는 어떤 방법으로도 볼 수 없습니다 — "다음 쪽"이 그대로 다음 장으로
넘어가 버리기 때문입니다. 마지막 단은 한 화면을 다 채우지 못한 자리에서 시작하므로
`columnPageAt()` 은 스크롤 폭까지 받아 "끝까지 갔으면 마지막 쪽"이라고 답하고,
`columnLeft()` 이 그 자리를 계산합니다.

한 쪽씩 보기에는 **CSS 스크롤 스냅을 쓰지 않습니다.** 단은 요소가 아니어서 스냅
지점을 가질 수 있는 것은 장 자체뿐이고, 그러면 스냅 지점이 장의 시작 하나입니다.
`scroll-snap-type: x mandatory` 는 반드시 스냅 지점에 멈추게 하므로 스크롤이 매번
첫 쪽으로 끌려 돌아갔습니다 — 쪽 번호만 올라가고 본문은 그대로였고, 그래서 장의
나머지를 아예 볼 수 없었습니다. 쪽 넘김은 창 폭의 정확한 배수로 직접 옮기므로
스냅이 도울 일이 없습니다.

부드러운 스크롤(`behavior: 'smooth'`)은 시간이 걸리고, 그동안 `scrollTop` 은 중간
어딘가입니다. 그 값을 읽으면 빠르게 두 번 누른 것이 한 쪽만 넘어갑니다 —
`pendingTop` 에 "가고 있는 곳"을 적어 두고 그것을 기준으로 다음 목표를 잡습니다.
### 한 쪽씩과 이어보기 — 설정이 둘인 이유

"이어보기 ↔ 한 쪽씩"은 글과 쪽에서 뜻이 다릅니다. 글에서는 한 장의 종이를 CSS 단으로
나누는 일이고, 쪽에서는 낱장을 위아래로 잇는 일입니다. 기본값도 반대입니다 — 글은 한
줄기로 이어 읽는 편이 낫고, 쪽은 한 장씩 보는 것이 책에 가깝습니다. 그래서 설정도
둘입니다: `pageMode`(글)와 `pageFlow`(쪽). 어느 쪽을 쓰는지는 `view.pageModeKey(book)`
가 답하고, 툴바 단추·메뉴·설정 창이 모두 그 답을 씁니다. 하나로 합쳤다가는 한쪽의
기본값이 반드시 틀리게 됩니다.

쪽의 이어보기는 `BookView` 가 책의 모든 쪽에 `.page-slot` 자리를 하나씩 만들고, 읽고
있는 쪽 앞뒤 `FLOW_WINDOW` 장만 실제로 그리는 방식입니다. 그리지 않은 자리는 이미 그린
쪽에서 잰 크기(`slotSize`)로 높이를 잡아 두므로 스크롤바가 정직하고, 수천 장짜리 PDF도
캔버스 몇 장 값으로 넘길 수 있습니다. 스크롤 위치에서 지금 쪽을 읽어 `onGoToPage` 로
올리고, 반대로 목차나 쪽 번호로 건너뛰면 그 자리로 스크롤합니다. 둘을 구분하는 것은
"마지막으로 우리가 스크롤을 놓은 자리"(`flowTop`)입니다 — 그것이 없으면 쪽을 보고했다는
사실 자체가 다시 그 쪽 맨 위로 스크롤을 되돌려, 런은 영원히 스크롤되지 않습니다.

### 쪽이 창에 맞는 방식

고정 레이아웃의 크기 계산은 한 곳에서 나옵니다. `room` 은 한 쪽이 차지할 수 있는 자리
(패널 여백을 뺀 창, 펼침이면 반으로)이고, `view.computePageScale()` 이 거기에 맞는 배율을
냅니다. PDF는 그 배율로 pdf.js가 그리고, 그림은 같은 배율로 픽셀 크기를 받습니다 —
그림도 실제 픽셀로 잡기 때문에 "100 %"가 창 너비의 비율이 아니라 그림 본래 크기를
뜻합니다. 회전은 `.page-frame` 이 **돌아간 쪽의 자리**를 차지하고 그림은 그 안에서 제
가운데를 축으로 돌아가는 식입니다. 프레임은 크기를 알기 전에도 있습니다 — 나중에 끼워
넣으면 React가 `<img>` 를 새로 만들어 쪽을 두 번 읽고 깜빡였습니다.

파일을 열 때는 `view.FIT_TO_WINDOW` 가 확대 모드·배율·회전을 창 맞춤으로 되돌립니다.
확대와 회전은 파일에 딸린 것이지 읽는 사람에게 딸린 것이 아니어서, 앞 파일을 300 %로
보았다는 사실이 다음 파일에 대해 말해 주는 것은 없습니다. `.ebkr` 독서 파일이 적어 둔
보기 설정만 이 되돌림을 덮습니다.

### MOBI 한 파일에 책이 둘 — KF8

`.azw3`(그리고 일부 `.azw`)는 MOBI 6의 새 판이 아니라 **다른 형식**입니다. 같은 Palm
데이터베이스 안에 책이 둘 들어 있을 수도 있습니다: 옛 MOBI 6 한 권과 KF8 한 권이 각자
자기 record 0과 자기 표를 가지고 나란히 있고, 첫 record 0의 **EXTH 121** 이 두 번째가
시작하는 레코드 번호를 말해 줍니다. 그래서 헤더는 파일당이 아니라 **파트당** 읽고
(`readPartHeader`), 파트 안의 모든 레코드 번호는 그 파트의 시작에서 셉니다.

KF8은 MOBI 6처럼 페이지 나누기로 자를 수 있는 하나의 HTML 덩어리가 아닙니다:

* **FDST** 가 한 줄기 바이트 흐름을 *flow* 로 나눕니다. flow 0이 본문이고 나머지는
  스타일시트·SVG 같은 것들입니다.
* **골격(SKEL) 인덱스** 가 각 XHTML 파트의 *틀*(`<html>…<body>` 껍데기)이 flow 0의
  어디에 있는지 말합니다.
* **조각(FRAG) 인덱스** 가 그 틀 안에 들어갈 조각들과, 어느 틀의 어느 위치에
  들어가는지를 말합니다.

파트는 틀을 가져와 조각들을 다시 꿰매어 만듭니다(`kf8.buildParts`). 이것을 하지 않으면
틀과 조각이 번갈아 늘어선 markup이 그대로 나오는데, 그것이 예전에 `.azw3` 가 "열리기는
하지만 읽을 수 없었던" 이유입니다.

**모든 오프셋은 바이트입니다.** UTF-8에서 한글은 한 자에 세 바이트이므로, 디코딩한
문자열을 그 숫자로 자르면 장이 하나씩 지날수록 어긋나 문장 중간에서 시작합니다 — 그래서
재조립은 바이트로 하고 완성된 파트만 디코딩합니다.

두 표는 모두 **INDX** 구조이고 `lib/indx.js` 가 읽습니다. 항목의 어떤 필드가 무엇인지는
항목 안에 없고 **TAGX** 블록에 있으며, 어떤 필드가 실제로 들어 있는지는 항목 앞의 제어
바이트가 말합니다 — 그래서 TAGX 없이는 한 항목도 읽을 수 없고, 디코딩하지 않고 건너뛸
수도 없습니다.

그림과 글꼴은 본문 뒤의 레코드이고 markup은 `kindle:embed:0009?mime=...`(**32진수**)로,
책 안 링크는 `kindle:pos:fid:0003:off:...`로 가리킵니다. 둘 다 읽기 창이 아는 형태로
바꿉니다.

압축은 셋 다 읽습니다: 무압축, PalmDOC LZ77, 그리고 **HUFF/CDIC**(`lib/huffcdic.js`) —
한 바이트가 아니라 *구절*을 가리키는 허프만 부호이고, 구절 자체가 또 압축되어 있을 수
있어 해독이 재귀적입니다. 비트 창은 64비트를 네 바이트씩 밀며 읽습니다.

DRM이 걸린 파일은 **열지 않고 그 이유를 말합니다.** DRM 해제는 구현하지 않습니다.

시험은 `scripts/make-samples.mjs` 가 KF8 책(`sample.azw3`), 두 권이 든 파일
(`sample-dual.azw3`), HUFF/CDIC로 압축된 MOBI(`sample-huff.mobi`)를 **직접 써서** 합니다.
INDX·TAGX·IDXT·CNCX·FDST를 쓰는 코드가 저장소 안에 있다는 뜻인데, 그것이 판독기를
"모든 필드를 아는 파일"에 대고 시험할 수 있는 유일한 방법입니다. HUFF 샘플의 표는
부호 길이가 모두 8비트인 가장 단순한 허프만 부호라서 **부호화한 바이트가 원문 바이트와
같습니다** — 디스크의 바이트가 알려져 있으므로 비트 창이나 사전을 잘못 다루면 눈에 보이게
다른 결과가 나옵니다.

### 브라우저가 못 읽는 그림

TIFF와 DICOM은 Chromium이 디코딩하지 못합니다. `lib/tiff.js` 는 baseline TIFF를
(무압축 · PackBits · LZW · Deflate, 8/16비트, 흑백 · 팔레트 · RGB(A)) 풀고,
`lib/dicom.js` 는 DICOM 요소를 훑어 크기 · 비트수 · 광도 해석 · 윈도 레벨을 읽어
화면에 맞는 밝기로 바꿉니다. 둘 다 **바이트 → RGBA** 의 순수 함수라 캔버스 없이
단위 시험할 수 있고, 캔버스는 결과를 그릴 때만 쓰입니다. 압축 DICOM 중 JPEG 프레임은
브라우저에 그대로 넘기고, JPEG 2000 · JPEG-LS · RLE 은 추측하지 않고 그렇다고 알립니다.

`detectFormat()` 은 **확장자보다 내용을 먼저** 믿습니다. 잘못된 이름으로 저장된
책(`.epub` 인데 PDF)이 흔하기 때문이고, 확장자는 ZIP처럼 내용만으로 가를 수 없는
경우(EPUB ↔ CBZ)에만 결정에 쓰입니다.

### 왜 ZIP·DEFLATE를 직접 구현했는가

EPUB과 CBZ는 ZIP입니다. 브라우저의 `DecompressionStream` 은 비동기 스트림이라
"필요한 장만 즉시 꺼내 쓰는" 구조와 맞지 않고, 런타임에 따라 없을 수도 있습니다.
`lib/inflate.js` (RFC 1951)와 `lib/zip.js` 는 순수 함수라 **단위 테스트가 쉽고**,
중앙 디렉터리만 읽어 두었다가 **요청받은 항목만** 풀기 때문에 500 MB 만화책도
첫 장을 여는 속도가 작은 책과 같습니다. 테스트는 Node의 zlib이 압축한 데이터를
풀어 보며 검증합니다 — 우리 코드끼리 서로 옳다고 우기지 않도록.

## 3. 본문 정화 (lib/html.js)

책의 본문은 **믿을 수 없는 파일에서 온 HTML**이고, 그것을 앱 자신의 문서 안에
그립니다. 그래서 `sanitizeChapter()` 가

* `<script>` `<iframe>` `<object>` `<form>` … 을 제거하고
* `on*` 이벤트 속성과 `style` · `class` 를 지우고 (앱이 직접 만든 `fb2-*` 클래스만 예외)
* `javascript:` URL을 막고
* 그림은 **책 안의 자원**으로 다시 연결하고 (blob: URL)
* 링크는 `href` 대신 `data-section` / `data-external` 로 바꿉니다

작성자 CSS를 버리는 것은 보안 때문만이 아닙니다. 글꼴 · 크기 · 줄 간격 · 폭 · 테마는
**독자의 설정**이고, 책의 스타일시트는 그 설정과 싸웁니다.

## 4. 표시와 독서 파일

원본 책은 절대 고쳐 쓰지 않습니다. 책갈피 · 형광펜 · 메모 · 읽던 위치는
`lib/library.js` 가 **`.ebkr`(JSON)** 로 저장합니다. 이것이 설치 프로그램이 전용
아이콘과 함께 등록하는 이 앱의 **문서 형식**입니다.

형광펜은 좌표가 아니라 **글자 자체**에 붙습니다. 흘러가는 본문은 글자 크기만 바꿔도
같은 문장이 다른 자리로 가기 때문입니다. `BookView.paintMarks()` 가 그리기 직전에
해당 문장을 찾아 감쌉니다.

실행 취소는 `lib/history.js` 의 **스냅샷 방식**입니다. 표시 상태는 작은 평범한
객체이므로, do/undo 쌍을 짝지어 관리하는 것보다 통째로 보관하는 편이 단순하고
"실행 취소: 형광펜" 같은 이름표가 공짜로 따라옵니다.

## 5. 메뉴와 대화상자는 진짜 창이다

`electron/childwindows.js` 가 **메뉴 창 1개 + 대화상자 창 풀**을 관리합니다.

* 프레임 없는 BrowserWindow는 자기 HTML을 잘라 냅니다. 그래서 목록이 긴 메뉴
  (최근 파일이 들어간 파일 메뉴, 40개 테마)는 **본체 밖으로 펼쳐질 수 없습니다.**
  메뉴를 별도 창으로 띄우면 화면 어디로든 넘어갈 수 있고, 한 열로 길게 늘어놓아도
  스크롤이 필요 없습니다. 그래도 화면보다 긴 메뉴는 있습니다 — 테마 40종. 이때는
  `MenuHost` 가 잰 높이가 화면을 넘으면 **단을 하나씩 늘려** 다시 재고(최대 4단),
  `MenuList` 가 행 수를 그리드 행 수로 넘겨 위에서 아래로 채운 뒤 다음 단으로
  넘어갑니다. 잘라 내거나 스크롤을 붙이지 않는다는 원칙은 그대로입니다.
* 대화상자도 같은 이유와, "팝업은 본체와 독립적이되 본체가 닫히면 함께 닫혀야 한다"는
  요구 때문에 **`setParentWindow(main)` 를 건 별도 창**입니다. 크기는 고정이고
  내부 스크롤이 없으며, 내용에 맞춰 창 높이를 스스로 보고합니다(`dialog:size`).
* 창을 매번 새로 만들면 그때마다 렌더러가 부팅되어 느립니다. 그래서 팝업 창은
  **이름 없는 경로**(`?popup=dialog`)로 미리 띄워 두고, 어떤 대화상자인지는 IPC로
  건네며, 닫힌 창은 파괴하지 않고 **풀에 되돌립니다.**

웹 빌드에는 두 번째 창이 없으므로 같은 본문(`components/dialogs.jsx`)을 인페이지
모달로 그립니다. 대화상자 본문은 스스로 닫거나 설정을 쓰지 않고 `onResult({action})`
로만 보고하기 때문에, 두 host가 서로 바꿔 끼워집니다.

## 6. 런타임 경계 (lib/platform.js)

렌더러 코드에는 `if (Electron)` 이 거의 없습니다. 파일 열기 · 저장 · 내려받기 ·
클립보드 · 인쇄 · 창 제어가 모두 이 한 파일 뒤에 있고,

| | Electron | 웹 |
| --- | --- | --- |
| 열기 | 네이티브 대화상자 + 경로 읽기(진행률) | `<input type="file">` |
| 저장 | 네이티브 저장 대화상자 | Blob 내려받기 |
| 인쇄 | 오프스크린 창 → 시스템 인쇄 | 새 창 → 브라우저 인쇄 |
| 클립보드 | `clipboard` 모듈 | 비동기 Clipboard API |
| 설정 | localStorage + `userData/settings.json` | localStorage |

오래 걸리는 작업은 모두 진행률을 보고하므로, UI가 진행 창을 띄울 수 있습니다.

### 창 밖에서 끌어다 놓은 것

놓인 것이 무엇인지 알아내는 일은 생각보다 여러 갈래입니다.

* **파일을 넘겨 준 경우** — `DataTransfer.files`. 그 파일이 디스크의 어디인지는
  `File.path` 가 알려 주었지만 Electron 32에서 없어졌고, 대신 `webUtils.getPathForFile()`
  이 답합니다. 렌더러에는 `webUtils` 가 없으므로 preload가 `pathForFile` 로 내주고,
  `platform.droppedPath()` 가 새 방법 → 옛 방법 순서로 물어봅니다. 지금 쓰는 31에서는
  둘 다 되지만, 올려도 조용히 망가지지 않습니다.
* **위치만 알려 준 경우** — 파일을 넘기지 않고 `text/uri-list` 에 `file://` URL만 주는
  프로그램이 많습니다. 예전에는 이 경우 아무 일도 일어나지 않았습니다.
  `platform.fileUrlToPath()` 가 `file:///C:/a%20b.epub` 를 `C:\a b.epub` 로,
  `file://server/share/x` 를 UNC 경로로 풀어 줍니다.
* **폴더인 경우** — 책이 아니라 폴더입니다. `fs:stat` 이 `isDir` 을 함께 알려 주고,
  폴더는 왼쪽 서재 패널에 열립니다(`openFolderAt`, 폴더 열기 명령과 같은 길). 파일로
  읽으려 하면 정체불명의 오류만 남습니다.
* **아무것도 아닌 경우** — 그렇다고 말합니다. 조용히 무시하면 앱이 고장 난 것처럼
  보입니다.

`dragover` 와 `drop` 둘 다에서 `preventDefault()` 를 불러야 합니다. 그러지 않으면
창이 브라우저처럼 그 파일로 **이동**해 버립니다(`will-navigate` 가 최후의 방어선으로
막아 두었습니다). 그리고 `dragleave` 는 창을 떠날 때만 오는 것이 아니라 들어오는 길에
지나치는 모든 요소에서 오므로, 강조 표시는 켜고 끄는 것이 아니라 **세어야** 합니다 —
그러지 않으면 창을 가로지르는 동안 계속 깜빡입니다.

## 7. 창 크기와 쪽 넘김

툴바가 필요로 하는 폭은 **언어 · 글꼴 · 이름 표시 여부**에 따라 달라지므로 상수로
정할 수 없습니다. `Toolbar` 가 배치된 실제 너비를 재서 `win:setMinWidth` 로 알려
주고, 메인 프로세스가 그 값을 창의 최소 폭으로 씁니다 — 버튼이 가려지는 일이
없습니다.

**좌·우 패널도 같은 방식**입니다(`components/panelWidth.js`). 탭 이름은 언어와
글꼴에 따라 길이가 변하므로 `usePanelMinWidth` 가 한 프레임 동안 탭의 `flex` 를
풀어 각자 제 너비를 갖게 한 뒤 재고, 그 값을 패널의 최소 폭으로 삼습니다. 여기서
중요한 것은 **합이 아니라 가장 넓은 탭 × 탭 수**라는 점입니다 — 탭이 `flex: 1` 로
똑같이 나눠 갖기 때문이고, 합으로 계산했더니 239px 가 나와 242px 에서 "책갈피"가
잘렸습니다. 끌어서 줄일 때도 이 값 아래로는 내려가지 않습니다.

**왼쪽 패널은 한 패널 안의 두 단**입니다. 도구(목차·서재·책갈피·찾기)는 왼쪽 가장자리를
세로로 가득 채우는 **레일**이고 — 세워 놓은 도구 모음입니다 — 고른 도구의 내용은 그
오른쪽에 붙습니다. 레일은 아이콘만 쓰고 이름은 툴팁으로 갑니다. 언어가 무엇이든 레일이
읽는 자리를 거의 먹지 않기 때문입니다. 최소 폭 계산도 달라집니다: 레일은 세로라서 **가장
넓은 하나**면 충분하고(`stacked`), 대신 **옆에 설 내용의 몫**(`beside`)을 더해야 합니다 —
칸막이를 끝까지 당겨도 내용이 실오라기가 되지 않습니다.

쪽 넘김 효과는 `BookView` 가 지금 보고 있는 자리(`장:단`)의 변화에서 방향을 계산해
한 번만 도는 클래스를 붙이는 것으로 끝납니다. 움직임 자체는 CSS에만 있고
(`turn-slide` · `turn-flip`), `prefers-reduced-motion` 에서는 아무것도 움직이지
않으며, 효과를 "없음"으로 두면 클래스가 아예 붙지 않습니다.

### 움직이는 것은 떠나는 쪽이다

한 층이고, 그 밑에 읽고 있는 것이 있습니다.

층(`.turn-page`)은 **읽던 쪽의 복사본**이고, 도착한 쪽 위에 그려집니다. 움직이는 것은
이 층입니다 — 넘어가거나 밀려 나가고, 사라지고 나면 남는 것이 새 쪽입니다. 새 쪽은
한 번도 움직이지 않았고 처음부터 그 밑에 있었습니다. 책에서 다음 장이 넘기는 장 밑에
있는 것과 같습니다. 반대로 옛 쪽을 세워 두고 새 쪽을 밀어 넣으면 그것은 *새 쪽이
들어오는 것*이지 쪽을 넘기는 것이 아닙니다.

**효과는 `useLayoutEffect` 로 답니다.** 보통 효과는 브라우저가 그린 *뒤에* 돕니다 — 그래서
독자는 넘어간 쪽을 한 프레임 보고, 그러고 나서 효과를 봤습니다. 도착이 먼저 오고 여정이
나중에 온 셈입니다.

**고정 레이아웃**(PDF·만화·그림)에서 복사본은 사진입니다. 넘김이 준비되는 그 순간 캔버스에서
뜨는데(`facesNow`), pdf.js가 새 쪽을 칠하는 것은 한 프레임 뒤라서 그 순간 캔버스에는 아직
떠나는 쪽이 있습니다. 두 장씩 보기에서는 두 쪽을 다 뜹니다 — 넘어가는 것은 펼침 전체입니다.

**글의 장**은 둘로 갈립니다. 같은 장에서 한 단 옆으로 갈 때는 창이 그 위를 미끄러지므로
보던 쪽이 스스로 화면 밖으로 걸어 나갑니다 — 미끄러짐이 곧 효과이고, 층이 필요 없습니다.
장이 *교체*될 때는 스스로 움직이는 것이 없으므로 층을 씁니다. 복사본은 **마크업 자체**이고
(`shownChapter`가 읽던 장의 HTML과 그때의 단 위치를 들고 있습니다), 창 크기의 층에 얹습니다.

살아 있는 장을 그대로 움직이지 *않는* 이유가 있습니다. 장은 **모든 단을 합친 너비**의 한
덩어리라서 퍼센트가 책의 절반이고, 옮기면 단이 창 밖으로 나가 글자가 겹칩니다. 도착하는
장을 90px 밀어 넣어 본 적이 있고, GUI 시험의 "본문이 창 밖으로 나가지 않는다"가 그 자리에서
잡았습니다. 층은 창 크기라서 옮겨도 아무 배치에 영향이 없습니다.

**끝내는 타이머는 ref 에 둡니다.** 효과의 cleanup 으로 두면 효과가 다시 돌 때마다 취소되는데,
넘김이 진행되는 동안 효과는 여러 이유로 다시 돕니다(새 장이 쪽 수를 보고하는 것만으로도).
다시 돈 효과는 위쪽 early exit 으로 빠져 새 타이머를 걸지 않았고, 그래서 넘어가던 쪽이
책 위에 그대로 누워 있었습니다.

PDF 쪽의 캔버스는 **자리로 키를 줍니다**(`key={i}`, 쪽 번호가 아니라). 쪽 번호로 키를
주면 넘길 때마다 캔버스가 버려지고 새로 만들어져, 새 쪽이 그려지기 전까지 빈 상자가
되었다가 되돌아옵니다 — 그것이 넘긴 뒤의 울렁거림이었습니다. 자리로 키를 주면 캔버스가
제 크기와 픽셀을 그대로 들고 있다가 다시 칠해지므로, 크기를 따로 붙잡아 둘 필요도
없습니다(붙잡아 둔 상자가 캔버스와 1픽셀이라도 어긋나면 그 자체가 또 한 번의 흔들림).

장이 바뀌면 단도 첫 단으로 돌아가므로 한 번의 넘김이 두 번의 변화로 보입니다. 이것을
한 번으로 만드는 것은 **장이 곧 자리잡을 곳**(`장:0`)을 기억해 두는 일입니다 — 한 렌더
뒤에 단이 0이 되는 것은 그러면 움직임이 아니게 됩니다. 전에는 시간 창(`TURN_MS/2`)으로
막았는데, 그러면 빠르게 넘기는 독자는 한 장 걸러 한 장씩 효과를 잃었습니다. 이어보기에는
넘길 쪽이 없으므로 효과를 아예 걸지 않습니다 — 스크롤과 싸우게 됩니다.

## 7.5 갤러리 — 10만 권을 견디는 구조

처음 만든 서가는 표지까지 설정 파일 안에 넣었습니다. 수십 권까지는 문제가 없지만
그 이상은 불가능합니다 — 12 KB 표지는 base64로 16 KB, 10만 권이면 **1.5 GB**이고,
그 전부를 시작할 때 파싱해야 합니다. 그래서 셋으로 나눴습니다.

| | 무엇 | 어디에 | 언제 쓰나 |
| --- | --- | --- | --- |
| 색인 | 책 한 권당 작은 레코드(경로·제목·지은이·형식·크기·쪽수) | `gallery/index.json` (웹: IndexedDB) | 서재에 책이 늘거나 빠질 때만 |
| 읽던 위치 | 경로 → 쪽 번호 | `gallery/positions.json` | 쪽을 넘길 때마다(작다) |
| 표지 | 카드 한 장 크기 PNG, 한 권당 한 파일 | `gallery/covers/<해시>.png` → `app://covers/…` | 그 카드가 화면에 보일 때만 |

읽던 위치를 따로 둔 이유는 측정에서 나왔습니다. 위치를 색인에 함께 쓰면 쪽을 넘길
때마다 23 MB를 다시 쓰게 되고, 그 사이 갤러리를 열면 눈에 띄게 늦습니다.

화면 쪽은 **창에 보이는 것만 만듭니다**(`windowOf`). 10만 권이어도 DOM에 있는 카드는
서른 몇 개뿐이고, 위아래 빈 블록이 나머지 자리를 대신하므로 스크롤 막대는 정직합니다.
표지는 카드가 생길 때 `<img>` 하나로 요청되고, 캐시와 폐기는 브라우저가 합니다.

실제 수치(스모크 검사, 10만 권):

```
색인 읽기 102ms · 파싱 51ms · 정렬 3ms          (23 MB)
갤러리 표시 20ms (패널 15ms) · DOM 카드 35개
서가 한가운데로 스크롤 15ms · DOM 카드 35개
```

측정 자체에도 함정이 있었습니다. 창이 앞에 없으면 Chromium이 타이머를 1초로 묶기
때문에, `setTimeout` 폴링으로 재면 20 ms짜리 동작이 1.5초로 보입니다. 그래서 시각은
**MutationObserver** 가 기록하고 검사는 그 값을 나중에 읽습니다.

## 7.6 갤러리의 나머지

`lib/gallery.js` 는 **읽은 책의 서가**입니다. 최근 파일 목록(10개, 파일 메뉴용)과는
다른 물건으로, 더 많은 책을 표지 · 지은이 · 형식 · 진행 · 마지막 읽음과 함께 들고
있습니다. 설정 파일에 함께 저장되므로 의도적으로 작게 유지합니다 — 개수 상한
(`MAX_GALLERY`)과, 표지를 카드 한 장 크기로 줄여 담는 `makeThumbnail`.

표지는 책이 가진 표지(`book.cover()`)를, 없으면 **지금 그려진 쪽**을 씁니다. 그래서
PDF · 만화 · 그림도 서가에서 알아볼 수 있습니다. 한 번 담은 표지는 다시 만들지
않고, 책을 다시 열어도 서가가 이미 아는 것(표지 · 읽던 자리)을 잃지 않습니다.

보기는 **큰 아이콘**과 **자세히** 두 가지이고 어느 쪽인지는 설정에 남습니다.
`Gallery` 컴포넌트 자체는 순수합니다 — 받은 목록을 그리고 "이 책을 열어라 · 이
책을 빼라 · 이렇게 정렬하라"를 보고할 뿐, 무엇도 스스로 바꾸지 않습니다.

그림 복사는 `BookView.pageImage()` 가 답합니다: 오른쪽 클릭한 그림, 없으면 쪽
그림, 없으면 PDF 캔버스. 캔버스가 오염되어 읽을 수 없으면 원본이 data URL 일 때만
그것을 돌려주고, 아니면 null 입니다 — 던지지 않습니다. 툴바의 단추도 메뉴 항목과
같은 조건으로 흐려집니다(`hasImage`): **쪽 자체가 그림인 책**(그림·만화·PDF)이거나,
글의 책이라면 **독자가 그림을 골라 두었을 때**. 전에는 책만 열려 있으면 눌렸고, 눌러도
"복사할 그림이 없습니다"만 나왔습니다.

### 표지가 없는 책의 표지

책 정보의 그림은 `lib/coverpage.js` 가 고릅니다: 책이 가진 표지, 없으면 **첫 쪽**.
표지 없는 책 — 텍스트 파일, 표지를 넣지 않은 PDF, 스캔 폴더 — 은 전에 아이콘이 박힌
회색 판을 받았는데, 그것은 책보다도 말해 주는 것이 없는 그림입니다. 첫 쪽은 책을 펼치면
어차피 보이는 것이고, 표지가 하는 일이 바로 그것입니다. 그리는 방법은 셋으로 갈립니다 —
그림은 `<img>`, 글의 장은 쪽 모양 상자 안에 줄인 본문, PDF 쪽은 캔버스에 칠하기. PDF는
`renderPage` 가 캔버스에 픽셀 크기를 박아 두므로, 칠한 뒤 그 인라인 크기를 **지워야**
합니다 — 폭은 상자에 맞춰 줄고 높이는 박힌 채로 남아 그림이 늘어졌습니다.

### 창을 재는 일이 렌더를 취소시키고 있었다

`BookView` 는 자기 창을 `ResizeObserver` 로 재서 `viewport` 에 넣습니다. 그 값이
**매번 새 객체**였던 탓에, 숫자가 그대로여도 상태가 바뀌어 다시 렌더되었습니다. 그리고
쪽은 그 창 크기에 맞춰 그려지므로 스크롤바가 생기거나 사라지며 관찰자가 또 울리는 —
끝나지 않는 왕복이 되었습니다. 그 렌더 하나하나가 PDF 쪽의 렌더를 취소시켰고, 글자 층이
중간에 취소된 쪽은 **선택할 글자가 아예 없는** 상태로 남았습니다. 이것이 "PDF 텍스트
선택이 될 때도 있고 안 될 때도 있다"의 정체입니다. 숫자가 실제로 달라졌을 때만 갱신하게
한 것이 고침입니다.

더해서 `renderTextLayer` 는 이제 글자 층을 **떼어 낸 곳에서 만들어 통째로 갈아 끼웁니다.**
먼저 비우고 나중에 채우는 방식은, 비운 뒤 취소되면 아무것도 되돌려 놓지 못하고 다시
시도할 계기도 남지 않았습니다. 화면의 층은 이제 *완성된* 층으로만 교체됩니다.

### 쪽 수는 글자로 센다

PDF·만화·그림의 쪽은 파일이 가진 것이라 세면 끝입니다. 글은 아닙니다 — EPUB 한 장은
창과 글꼴과 글자 크기가 정하는 만큼의 쪽이고, 창을 늘리면 달라지는 숫자는 "이 책 어디쯤"
을 말하는 데도, 남에게 위치를 알려 주는 데도 쓸 수 없습니다. 그래서 `lib/pages.js` 는
**인쇄된 쪽처럼 정해진 양의 글자**를 한 쪽으로 봅니다(`CHARS_PER_PAGE`). 어림셈이고 그렇게
표시하지만(`≈`), 흔들리지 않는 어림셈이며 그것이 쓸모 있는 종류입니다. 재려면 모든 장을
읽어야 하므로 열자마자 배경에서 몇 장씩 끊어 세고, 다 세면 상태 바에 나타납니다.

### 무엇이 골라졌는지 보이기

그림을 고르는 일은 `imageUnder()` 와 `pick()` 둘로 갈라집니다. PDF 쪽은 캔버스 위에
글자 층이 덮여 있어 클릭이 캔버스에 닿지 않습니다 — 그래서 `.pdf-page` 안을 눌렀으면
그 쪽의 캔버스로 보되, **글자 위(`.textLayer span`)를 눌렀을 때는 아무것도 고르지
않습니다**. 그때 독자가 하려는 일은 글 선택이고, 쪽 전체에 테두리를 두르면 그 일을
방해합니다. 고른 그림은 테두리만으로는 눈에 띄지 않으므로 `onPickImage` 로 App에
올려 상태 바가 "그림 선택됨 폭×높이" 칸을 내보이고, 놓으면 칸도 사라집니다.

글 선택도 형식마다 다른 것이어서 `selectAll()` 이 갈라 답합니다: 본문은 `.chapter`,
PDF는 쪽마다의 `.textLayer` 들을 아우르는 범위, 그림·만화는 고를 글자가 없으므로
`false` 입니다 — App이 그것을 받아 "선택할 글자가 없습니다"라고 말합니다. 조용히
아무 일도 하지 않는 것보다 낫습니다. PDF 글자 층은 `opacity: 1` 이어야 합니다:
글자 자체가 투명하므로 층의 불투명도를 낮추면 그 안에서 실제로 그려지는 단 하나,
선택 강조가 함께 흐려져 선택이 안 된 것처럼 보였습니다.

## 8. 테스트

```
test/
  inflate · zip · html · markdown · search · library · view · print   핵심 엔진
  epub · mobi · fb2 · cbz · plaintext · book · image                   책 형식
  settings · themes · menus · folders · platform                       설정·상태
  components · bookview · panels · dialogs · menuhost · app            GUI 동작
  i18n                                                                 언어
  package · electron-contract · icon-assets · reporter                 빌드·패키징
```

* **샘플 책**(`scripts/make-samples.mjs`)은 형식마다 진짜 파일을 만들어 둡니다.
  해석기는 그 파일들을 상대로 시험합니다 — 해석기의 가정에 맞춰 쓴 고정물이 아니라.
* **GUI**는 실제 컴포넌트를 렌더링해 버튼 · 메뉴 · 패널 · 대화상자 · 단축키 ·
  끌어다 놓기까지 눌러 봅니다. `app.test.jsx` 는 진짜 EPUB을 열어 읽고 표시하고
  찾고 인쇄합니다.
* **electron-contract** 는 preload가 노출하는 호출과 메인 프로세스가 처리하는
  채널이 정확히 맞는지 검사합니다. 여기는 타입 검사기가 없는 경계입니다.
* **팝업 레이아웃**은 `npm run shoot:dialog -- settings out.png` 로 그 창만 찍어
  눈으로 확인합니다 — 설정 창이 내용 없이 납작해졌던 것도 이렇게 찾았습니다
  (팝업 문서에 높이가 없어 flex 열이 무너진 것이 원인이었습니다).
* `npm run smoke` 는 같은 확인을 **진짜 Electron 창**에서 합니다: 메뉴가 별도
  창으로 떴는지, 최소 폭이 OS에 적용됐는지, 투명도가 실제 창에 걸렸는지.
  브라우저만 답할 수 있는 것들도 여기서 잽니다 — 넘긴 뒤 쪽이 **0px** 움직이는지,
  끄는 동안 보호 블록이 움직였다 제자리로 가는지, 목차로 뛰어다녀도 본문이 창
  밖으로 나가지 않는지, 글자 크기를 바꿔도 전체 쪽 수가 그대로인지.
* 스모크의 검사들은 **설정 파일을 공유**합니다. 한 검사가 바꾼 넘기기 방식이나
  글자 크기는 다음 검사에도, 다음 실행에도 남습니다. 그래서 검사는 필요한 상태를
  **스스로 만들고**(`setPageMode` · `setPageTurn` · `setTextScale`), 실패하더라도
  `finally` 로 되돌립니다 — 그러지 않으면 한 번의 실패가 여러 번의 실패가 됩니다.
* `npm run try:books` 는 저장소가 만든 샘플이 아니라 **실제 책**(기본값: 바탕화면)
  으로 같은 일을 합니다. 샘플은 우리가 쓴 파일이라 판독기가 우리 가정을 만족한다는
  것만 말해 줍니다. 실제 EPUB 한 권이 `<script/>` 하나 때문에 검색도 내보내기도
  쪽 수도 전부 비어 있던 것은 이 도구가 찾았습니다.
* 결과는 분류별로 묶여 출력되고, 마지막에 **칸이 맞는 요약 표**가 붙습니다
  (`test/reporters/summary.mjs`). 한글은 터미널에서 두 칸을 차지하므로
  `String.length` 가 아니라 표시 폭으로 자리를 맞춥니다.
