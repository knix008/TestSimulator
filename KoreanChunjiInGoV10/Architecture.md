# 설계 문서

## 출발점

이 저장소는 [KoreanChunJiInC++](../KoreanChunJiInC++) 를 Go 로 옮긴 것입니다.
원본은 Windows 전용이고 Win32 API 위에 붙어 있었습니다. 목표는 두 가지였습니다.

1. **조합 결과가 원본과 한 글자도 다르지 않을 것**
2. Windows · macOS · Linux · 웹 네 곳에서 돌 것

그래서 조합 엔진과 화면을 완전히 갈라 놓았습니다.
엔진은 운영체제를 하나도 모르고, 화면은 조합 규칙을 하나도 모릅니다.

## 계층

```
┌──────────────────────────────────────────────────────────┐
│ 데스크톱                        웹                        │
│ internal/ui  (Fyne)             web/ (HTML · CSS · JS)   │
│   창 · 메뉴 · 툴바 · 키패드       화면 · 키패드              │
│   테마 4종 · 언어 2종             테마 4종 · 언어 2종         │
├──────────────────────────────────────────────────────────┤
│ cmd/chunjiin                    cmd/chunjiin-wasm        │
│   (실행 파일)                     (엔진을 JS 로 내보냄)      │
├──────────────────────────────────────────────────────────┤
│ internal/engine   순수 Go · 의존성 없음 · GOOS 를 가리지 않음 │
│   chunjiin.go   원본 chunjiin.c  - 유니코드 조합, 겹받침     │
│   input.go      원본 input.c     - 오토마타, 편집 API        │
│   labels.go     라벨 · 모드 이름 · 상태줄                    │
└──────────────────────────────────────────────────────────┘
```

같은 `internal/engine` 이 데스크톱 실행 파일에도, WASM 에도 들어갑니다.
그래서 웹에서 친 "안녕" 과 데스크톱에서 친 "안녕" 이 다를 수가 없습니다.

## C++ 판과의 대응

| C++ | Go | 옮기면서 달라진 것 |
|---|---|---|
| `wchar_t text_buffer[4096]` | `[]rune` | 널 종료 대신 길이. 최대 글자 수는 4095 로 같다 |
| `wchar_t chosung[4]` | `string` | 낱자 하나를 담는 짧은 문자열 |
| `wchar_to_utf8()` | `State.Text()` | Go 문자열은 이미 UTF-8 이라 변환이 필요 없다 |
| `get_unicode()` 의 if 사슬 | 표 + `indexOf()` | 결과는 같다. 사슬 끝 기본값(ㅎ/ㅣ/ㅎ)도 그대로 둔다 |
| `check_double()` 의 if 사슬 | `map[string]map[string]string` | 같은 표 |
| `chunjiin_process_input()` | `State.Key(int)` | |
| `HKCU\Software\Chunjiin` | `settings.json` | 레지스트리는 Windows 에만 있다 |
| `IShellLinkW` 바로 가기 | 설치 프로그램이 PowerShell 로 만든다 | COM 의존을 줄인다 |

### 원본의 함정을 그대로 둔 곳

`get_unicode()` 는 초성이 비어 있으면 `cho` 를 `18`(=`ㅎ`)로 떨어뜨립니다.
그래서 **초성이 없는 상태에서는 종성을 채우면 안 됩니다.**
오토마타는 모음만 있는 상태에서 자음을 받으면 앞 글자를 확정하고
새 음절의 초성으로 넣습니다(`ㅏ` + `ㄱ` → `ㅏㄱ` 두 글자).
Go 판도 이 규칙을 그대로 지킵니다. 고치면 결과가 원본과 달라집니다.

## 상태

```go
type State struct {
    Hangul     HangulState   // 조합 중인 한 음절
    NowMode    InputMode
    Engnum     rune          // 영문/숫자/기호 모드에서 조합 중인 문자
    TextBuffer []rune
    CursorPos  int           // 삽입 위치

    // 아래는 원본 chunjiin.c 가 쓰지 않는 확장 필드
    LastKey       int          // 직전에 눌린 키, 없으면 -1
    TapCount      int          // 같은 키 연타 위치
    ComposeLen    int          // 조합 글자가 차지한 칸 수 (0~2)
    PrevSyllable  HangulState  // 겹받침 되돌려 붙이기용
    PrevMergeable bool
}
```

### 조합 중인 글자를 화면에 두는 방법

조합 중인 글자는 **`CursorPos` 바로 앞의 `ComposeLen` 칸**에 놓입니다.

```
TextBuffer : 안 녕 하 세 요 ㄱ ·
                                ^ CursorPos
                          └──┬──┘
                        ComposeLen = 2
```

`writeHangul()` 은 매번 그 칸들을 지우고 새로 그립니다.
음절이 확정되면 `ComposeLen` 을 0 으로 만듭니다. 그러면 이미 찍힌 칸이
그대로 확정 글자가 되고, 다음 글자는 새 칸에 들어갑니다.
따로 "확정 버퍼" 와 "조합 버퍼" 를 나눌 필요가 없습니다.

### 겹받침 되돌려 붙이기

받침 뒤에 온 자음이 겹받침을 이루지 못하면 새 음절로 떨어져 나갑니다.
그런데 자음 키는 순환하므로, **한 번 더 누르면 겹받침이 되는 자음이 나올 수
있습니다.**

```
만 + ㅅㅎ 키   ->  만ㅅ      (ㄴ+ㅅ 은 겹받침이 아니다)
     ㅅㅎ 키   ->  많        (ㄴ+ㅎ 은 ㄶ 이므로 도로 합친다)
```

이걸 위해 `State` 가 직전 음절을 `PrevSyllable` 에 들고 있습니다.
`tryMergeJong()` 이 순환 후보 중에 앞 음절의 받침과 합쳐지는 것을 찾으면,
`ComposeLen` 을 하나 늘려 **앞 칸까지 조합 영역으로 끌어들인 뒤** 다시 그립니다.
두 칸이 한 칸이 됩니다.

이 장치가 없으면 `ㄶ ㄻ ㄾ ㅀ` 이 들어간 글자(`많 삶 핥 옳`)를 아예 입력할 수
없습니다. 순환 첫 자리(`ㅅ ㅇ ㄷ`)가 겹받침을 못 이루기 때문입니다.

`PrevMergeable` 은 모음 · 문장부호 · 확정 · 백스페이스 · 커서 이동이 오면
바로 꺼집니다. 직전 키를 한 번 더 누른 경우에만 살아 있습니다.

### 아래아 중간 상태

`GetUnicode()` 는 중성이 `·` 나 `‥` 이면 0 을 돌려줍니다(아직 모음이 아니므로).
그대로 두면 아래아를 누르는 동안 화면에 아무것도 안 보입니다.
그래서 `composeDisplay()` 가 그 경우만 따로 처리합니다.

```
초성 없음 + ·   →  "·"        (1칸)
초성 ㄱ  + ·    →  "ㄱ·"      (2칸)
초성 ㄱ  + ‥    →  "ㄱ‥"      (2칸)
```

초성만 있을 때의 호환 자모(`ㄱ`)를 얻으려고 중성을 잠깐 비운 뒤
`GetUnicode()` 를 부르고 되돌립니다. 원본을 고치지 않고 원하는 값을 얻는
방법이고, Go 판도 같은 수를 씁니다.

## 오토마타

### 모음

`vowelRules` 는 (현재 중성, 누른 키) → 다음 중성 전이표입니다.
`noVowel` 이면 그 조합은 없으므로 앞 글자를 확정하고 새 음절을 시작합니다.
`prev` 열은 백스페이스로 한 단계 되돌릴 때 씁니다.

```go
//  from    ㅣ        아래아     ㅡ         prev
{"",     "ㅣ",    "·",     "ㅡ",     ""},
{"·",    "ㅓ",    "‥",     "ㅗ",     ""},
{"ㅗ",   "ㅚ",    "ㅛ",    noVowel,  "·"},
{"ㅚ",   noVowel, "ㅘ",    noVowel,  "ㅗ"},
```

`ㅝ` 는 `ㅠ` + `ㅣ` 로 들어옵니다. `ㅠㅣ` 라는 모음이 없기 때문에
그 자리를 `ㅝ` 로 쓰는 것이 천지인의 규칙입니다.

### 자음

`consCycle` 은 키마다 순환 목록을 갖습니다(`ㄱ ㅋ ㄲ`).
같은 키가 연달아 오면 순환하고, 그렇지 않으면 자리(초성 → 종성 → 겹받침)를
채웁니다.

순환 대상이 종성이면 `isValidJong()` 으로 걸러서 `ㄸ ㅃ ㅉ` 이 받침에 들어가지
않게 하고, 겹받침 자리면 `CheckDouble()` 로 실제로 합쳐지는지 확인합니다.

### 연음

받침이 있는 상태에서 모음 키가 오면, 마지막 자음을 떼어 새 음절의 초성으로
옮깁니다.

```
간(ㄱ ㅏ ㄴ) + ㅏ
  → 받침 ㄴ 을 떼고 "가" 확정
  → 새 음절 초성 ㄴ + 모음 ㅏ = "나"
```

겹받침이면 두 번째 자음만 넘어갑니다(`값` + 모음 → `갑` + `사...`).

### 연타 순환을 끊는 시점

`안녕` 처럼 같은 키가 연달아 필요할 때를 위해 `BreakMultitap()` 이
`LastKey` 를 지웁니다. 화면 쪽이 두 곳에서 부릅니다.

- 키 입력 뒤 정해 둔 시간(기본 0.8초)
- 커서 이동 · 확정 계열 동작 (`→`, `←`, `Esc`, 스페이스 등은 `Commit()` 이 겸함)

## 데스크톱 화면 (internal/ui)

### 엔진이 원본, 화면은 거울

어떤 동작이든 엔진을 건드린 뒤 `refresh()` 한 번을 부르면 화면 전체가
맞춰집니다. 화면이 따로 상태를 들고 있지 않으므로 어긋날 자리가 없습니다.

```go
func (a *App) doKey(i int) {
    a.state.Key(i)      // 엔진을 건드리고
    a.refresh()         // 화면을 다시 그린다
    a.restartTapTimer()
}
```

### 편집 영역

Fyne 의 `widget.Entry` 를 쓰되 **직접 타이핑하지 못하게** 막습니다.
`TypedRune` / `TypedKey` / `TypedShortcut` 을 모두 가로채 엔진으로 넘깁니다.
C++ 판이 읽기 전용 `EDIT` 컨트롤을 서브클래스해서 하던 일과 같습니다.

엔진은 커서를 "몇 번째 글자" 하나로 들고, `Entry` 는 (줄, 칸) 두 값으로
듭니다. `rowColOf()` / `flatPosOf()` 가 그 사이를 옮깁니다.

### 커서를 늘 보이게

키패드 버튼은 초점을 받지 않는 위젯이라, 누르면 Fyne 이 편집 영역의 초점을
풀어 버립니다. 그러면 깜박이는 커서가 사라져서 어디에 글자가 들어갈지 알 수
없습니다. 그래서 `refresh()` 끝에서 초점을 도로 가져옵니다.
대화 상자가 떠 있을 때는 건드리지 않습니다.

### 버튼

키패드 버튼과 툴바 버튼은 Fyne 의 기본 위젯을 쓰지 않고 직접 그립니다.
역할(자음 / 모음 / 문장부호 / 기능 / 모드 / 툴바)마다 색이 달라야 하는데,
Fyne 테마는 위젯 하나하나에 다른 색을 주지 못하기 때문입니다.
C++ 판이 `BS_OWNERDRAW` 로 하던 일과 같습니다.

### 글꼴

Fyne 의 기본 글꼴에는 한글이 없어서 **Noto Sans KR 을 실행 파일에 넣습니다.**
완성형 11172자를 모두 담고 있어야 `갂 갃` 같은 글자도 그려집니다.

가변 글꼴 `NotoSansKR[wght].ttf` 를 그대로 넣으면 안 됩니다.
그 글꼴은 `wght` 축의 **기본값이 100(Thin)** 이라서 글자가 아주 가늘게,
흐릿하게 나옵니다. 그래서 400 과 700 으로 미리 뽑아 둔 두 벌을 넣습니다.

```sh
python -m fontTools.varLib.instancer -o NotoSansKR-Regular.ttf NotoSansKR[wght].ttf wght=400
python -m fontTools.varLib.instancer -o NotoSansKR-Bold.ttf    NotoSansKR[wght].ttf wght=700
```

버튼과 상태줄은 `canvas.Text` 의 `FontSource` 로 글꼴을 못박습니다.
테마를 거치는 경로는 글꼴 캐시를 타서 굵기가 제때 반영되지 않는 일이 있습니다.

글꼴에 없는 글자를 라벨로 쓰면 버튼이 빈칸으로 나옵니다. `↵`(U+21B5)와
`⌫`(U+232B)가 Noto Sans KR 에 없어서 실제로 겪은 일입니다. 그래서 그 두
자리는 글자가 아니라 직접 그린 그림(`icons.go`)을 씁니다. 글자로 적는
자리는 `TestFnLabelGlyphs` 가 내장 글꼴에 그 글자가 있는지 확인합니다.

### 테마

색은 모두 `Palettes` 표에서 가져옵니다. C++ 판 `THEMES[]` 와 같은 값입니다.
창 배경 · 카드 · 테두리 · 글자 · 흐린 글자와, 버튼 역할마다 다섯 가지 색
(기본 · 호버 · 눌림 · 테두리 · 글자)을 갖습니다.

`appTheme.Color()` 는 팔레트만으로 모든 색을 냅니다. 모르는 이름을 Fyne 기본
테마로 넘기지 않습니다. 기본 테마의 `Color` 는 `fyne.CurrentApp()` 을 거치므로
앱이 뜨기 전이나 시험 중에는 죽기 때문입니다.

### 언어

`Strings` 구조체 하나에 화면에 나오는 모든 글자가 들어 있습니다.
구조체이므로 **항목을 하나 빠뜨리면 컴파일이 되지 않습니다.**
`TestLangTablesComplete` 가 두 언어의 모든 칸이 비지 않았는지 전수로 봅니다.

### 배치

5행 구조입니다. 위 4행은 3열 균등, 마지막 행은 기능 버튼 6개를 비율로
나눕니다. `x` 좌표를 누적 비율로 계산해서 반올림 오차가 쌓이지 않게 합니다.

```go
var fnWeight = []int{7, 4, 10, 4, 4, 6}   // 합 35
```

C++ 판과 같은 값입니다. 그쪽도 화살표·줄바꿈·지우기를 아이콘으로 그렸습니다.

### 설정

`Settings` 를 JSON 파일 하나로 저장합니다.

```
Windows  %AppData%\Chunjiin\settings.json
macOS    ~/Library/Application Support/Chunjiin/settings.json
Linux    ~/.config/Chunjiin/settings.json
```

경로를 만드는 함수는 변수로 두었습니다. 시험이 그것을 갈아 끼워 임시 폴더를
쓰게 하기 위해서입니다. 환경 변수를 건드리는 것만으로는 운영체제마다 다른
`os.UserConfigDir` 를 확실히 돌려세울 수 없어, 실제 사용자 설정을 덮어쓸
위험이 있었습니다.

## 웹 화면 (web/)

조합은 하나도 자바스크립트에서 하지 않습니다.
키를 누르면 `chunjiin.wasm` 으로 넘기고, 돌아온 상태 객체로 화면을 다시
그립니다.

```
누름 → chunjiin.key(i) → 상태 객체 → render(상태)
```

`cmd/chunjiin-wasm` 이 엔진 함수들을 `window.chunjiin` 에 붙여 줍니다.
**모든 함수가 처리를 마친 뒤의 상태 객체를 돌려주므로**, 부른 쪽은 따로
상태를 다시 물을 필요가 없습니다.

- 편집칸은 진짜 `<textarea>` 입니다. 그래야 브라우저가 커서 · 선택 · 스크롤을
  맡아 줍니다. `beforeinput` 을 막아 직접 편집은 못 하게 합니다.
- 글꼴은 내려받지 않고 시스템 한글 글꼴을 씁니다. 더 또렷하고, 6MB 짜리
  글꼴을 받게 하지 않아도 됩니다.
- 색은 CSS 변수로 두고 `<body data-theme="...">` 를 갈아 테마를 바꿉니다.
  값은 데스크톱 판 `Palettes` 와 같습니다.
- 설정은 `localStorage` 에 넣습니다.
- 툴바 아이콘은 인라인 SVG 입니다. 이모지를 쓰면 시스템마다 색과 크기가
  달라집니다.

WASM 은 약 1.8 MB 입니다. Fyne 을 그대로 웹으로 올리면 글꼴까지 얹혀
20~30 MB 가 되므로, 웹만 따로 HTML 로 그리는 편을 골랐습니다.

## 설치 프로그램

`cmd/chunjiin-setup` 은 C++ 판 `installer/setup.c` 와 같은 생각입니다.
실행 파일을 `go:embed` 로 자기 안에 품고 있다가 설치 폴더에 풉니다.
관리자 권한이 필요 없고, 다른 설치 도구를 깔지 않아도 됩니다.

- **Windows** — 실행 파일을 놓고, `cscript` 의 `WScript.Shell` 로 시작 메뉴
  바로 가기를 만들고, `HKCU\...\Uninstall\Chunjiin` 에 등록 정보를 씁니다.
  설정 > 앱 제거는 작은 `uninstall.bat` 가 맡습니다. 설치 프로그램 자신을
  복사하지 않습니다.
- **Linux** — `~/.local/share/Chunjiin` 에 놓고, `~/.local/bin` 에 링크를 걸고,
  `.desktop` 항목과 아이콘을 만듭니다.
- **macOS** — `~/Applications/Chunjiin.app` 묶음을 만듭니다.

품고 있는 실행 파일은 `scripts/package.*` 가 빌드해서 `payload/` 에 넣고,
설치 프로그램을 빌드한 뒤 지웁니다. 저장소에 남지 않습니다.

## 시험

### 기대값을 손으로 옮겨 적지 않는다

조합 규칙의 기대값은 C++ 판 `tests/test_engine.c` 에 이미 585항목이 있습니다.
그걸 Go 로 옮겨 적으면, 원본이 고쳐졌을 때 조용히 어긋납니다.
그래서 **그 파일에서 직접 뽑아 옵니다.**

```
KoreanChunJiInC++/tests/test_engine.c
        │
        │  go generate ./test/
        │  (cmd/gen-testcases 가 훑는다)
        ▼
test/cases.tsv                          27구역 430항목
        │
        │  test/cases_test.go 가 읽어 돈다
        ▼
   go test ./...
```

뽑아낸 결과는 저장소에 함께 둡니다. C++ 판이 없는 곳에서도 시험은 그대로
돌아갑니다.

뽑아 오는 것은 `expect` 계열 호출과 표로 적힌 줄입니다.
C 코드에서도 계산으로 만들어지는 것(영문 26자 전수, 라벨-입력 일치)과
원본 함수를 직접 부르는 것(`get_unicode`, `check_double`)은 뽑을 수 없어
`test/engine_test.go` 에 Go 로 적어 둡니다.

시험은 두 자리에 있습니다.

| 자리 | 무엇 | 왜 거기인가 |
|---|---|---|
| `test/` | 엔진 시험과 시험 자료 | 엔진은 공개 API 만으로 다 볼 수 있다 |
| `internal/ui/` | 화면 시험 | Go 는 패키지 안의 비공개 이름을 그 패키지의 시험만 보게 한다 |

### 비교 축

| 종류 | 확인하는 것 |
|---|---|
| `expect` | 확정 후 텍스트 버퍼 |
| `live` | 확정하지 않은, 조합 중인 화면 |
| `cursor` | 버퍼 + 커서 위치 |
| `comp` | 상태줄 조합 표시 |
| `mode` | 모드 이름 |

### 시험이 스스로를 지키는 장치

- `TestCasesFileShape` — 뽑아 온 항목이 430개인지 본다. 뽑개가 조용히 망가지면
  시험이 통째로 비어도 통과해 버리기 때문이다.
- `TestKeyLabels` — 다섯 모드 × 12키. 버튼에 적힌 글자와 실제로 들어가는
  글자가 같은지 본다.
- `TestFnLabelGlyphs` — 기능 버튼 라벨의 모든 글자가 내장 글꼴에 있는지 본다.
- `TestLangTablesComplete` — 두 언어 글자표에 빈 칸이 없는지 본다.
- `TestThemeColors` — 테마가 어떤 색 이름에도 `nil` 을 주지 않는지 본다.
- `TestWeightedRow` — 기능 버튼 줄이 오른쪽 끝에 정확히 닿는지 본다.
- `TestCursorRoundTrip` — 커서 표현 두 가지를 오갔을 때 제자리로 오는지 본다.

- `TestAppSmoke` — 창과 단추를 실제로 만들어 화면 배선을 본다.
  KoreanChunjiinJavaV10 의 `AppSmokeTest.java` 에 해당한다. 그쪽은
  java.awt.Robot 을 써서 화면이 없으면 건너뛰었지만, 여기서는 Fyne 의
  시험용 드라이버를 쓰므로 화면 없이도 그대로 돈다.
- `TestAppTooltipLayer` — 툴팁 조각이 마우스를 가로채지 않는지 본다.
  가로채면 버튼이 MouseOut/MouseIn 을 되풀이하며 깜빡인다(실제로 겪은 일).

전부 합쳐 722항목입니다.

### 결과를 어떻게 보여 주는가

`go test` 는 꾸러미마다 ok/FAIL 만 찍어서, 무엇을 얼마나 보고 있는지
알 수 없습니다. C++ 판 `test_engine` 은 구역별 집계와 전체 요약을
보여 주었는데 그 편이 훨씬 낫습니다. 그래서 `cmd/testreport` 가
`go test -json` 을 읽어 같은 모양으로 정리합니다.

- 묶음(`조합 엔진 · C++ 원본에서 뽑아 온 자료` 등)과 구역으로 나눕니다.
- 하위 항목을 가진 시험은 세지 않습니다. 그것까지 세면 두 번 세게 됩니다.
- 각 시험이 `t.Log` 로 남긴 한 줄을 `-v` 에서 항목 옆에 보여 줍니다.
  이름만으로는 그 항목이 무엇을 보는지 알 수 없기 때문입니다.
- 실패하면 어느 구역의 어느 항목이 왜 틀렸는지 따로 모아 보여 줍니다.

보고기 자체도 시험합니다(`cmd/testreport/report_test.go`).
보고기가 조용히 망가지면 "0개 중 0개 통과" 같은 헛된 요약이 나오고,
그것을 보고 다 잘 돌아간다고 믿게 되기 때문입니다.
