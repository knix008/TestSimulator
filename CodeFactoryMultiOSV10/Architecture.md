## 1. 큰 그림

```
                 ┌──────────────────────────────────────┐
                 │            src/core/                 │
   플랫폼 무관 →  │   분석 엔진 (의존성 0, DOM 접근 0)   │
                 │   브라우저·Electron·node --test 동일  │
                 └───────────────┬──────────────────────┘
                                 │ analyze(files, settings)
                 ┌───────────────┴──────────────────────┐
                 │      src/worker/analyzer.worker.js   │
                 │  Web Worker — 메인 스레드를 막지 않음 │
                 └───────────────┬──────────────────────┘
                                 │ postMessage(result)
   ┌─────────────────────────────┴───────────────────────────────┐
   │                          src/App.jsx                        │
   │        분석 수명주기 · 메뉴 · 툴바 · 창 · 내보내기          │
   └───┬──────────────────┬───────────────────┬──────────────────┘
       │                  │                   │
 src/views/         src/report/        src/platform/adapter.js
 (뷰 15종)      (문서 모델 + 4개 포맷)   Electron ↔ Web 어댑터
```

핵심 규칙: **`src/core/`는 플랫폼 API를 전혀 모릅니다.** `window`, `fs`, `document`를
쓰지 않고 순수 데이터만 다룹니다. 그래서 같은 코드가 브라우저 워커, Electron, `node --test`에서
똑같이 돌아가고, 테스트가 실제 동작을 검증한다고 말할 수 있습니다.

### 3.1 마스킹이 핵심이다

`maskSource(source, languageId)`는 **주석과 문자열 내용을 공백으로 바꾸되
길이·개행·오프셋을 그대로 유지한** 사본을 만듭니다.

```
원본:  function f() { const s = "}"; return 1; }
마스킹: function f() { const s = " "; return 1; }
```

모든 구조 스캔(선언 인식, 괄호 매칭, 호출 검출)은 **마스킹된 사본**에서 돌아갑니다.
그래서 문자열 안의 `}`가 함수 본문을 끊거나, 주석 안의 `def`가 함수로 잡히는 일이
원리적으로 일어나지 않습니다. 반대로 리터럴 내용이 증거인 분석
(SQL 캡처, 하드코딩 비밀 탐지)은 **원본**을 읽습니다.

이 한 가지 결정이 정규식 기반 분석기의 오탐 대부분을 없앱니다.

### 3.2 본문 범위 확정

언어를 세 부류로 나눕니다.

| family | 본문 끝 판정 | 언어 |
|--------|--------------|------|
| `brace` | `{`의 짝 찾기 | C#, Java, C/C++, JS/TS, Go, Rust, Swift, Kotlin, PHP |
| `indent` | 들여쓰기가 선언 수준으로 돌아올 때까지 | Python |
| `keyword` | `end` / `End Sub` / `End Function` | Ruby, VB.NET |

선언만 있고 본문이 없는 것(인터페이스 메서드, C++ 프로토타입)은 `;`를 만나 `null`을
돌려주므로 함수 목록에 들어가지 않습니다.

### 3.3 호출 해석

호출 이름을 **같은 파일 → 같은 디렉터리 → 같은 언어 → 전역** 순으로 해석합니다.
해석되지 않는 이름(라이브러리 호출, 동적 디스패치)은 **추측하지 않고 버립니다.**
그래서 fan-in/out은 "그래프에 포함된 함수에 한해" 의미가 있습니다.

### 3.4 결정론

레이아웃을 포함해 **모든 것이 결정론적**입니다. 힘 기반(force-directed) 배치를 쓰지 않는 이유가
여기 있습니다 — 같은 프로젝트가 실행할 때마다 다르게 그려지면 두 내보내기를 비교할 수 없고
"박스가 움직였다"가 아무 의미도 없는 관찰이 됩니다.
`analyze.test.mjs`에 두 번 실행 결과가 정확히 같은지 확인하는 테스트가 있습니다.

## 5. 보고서

`src/report/builder.js`가 분석 결과를 **구조화된 문서**로 바꿉니다.
블록 종류는 `heading · paragraph · table · list · keyValue · callout · chart` 7가지뿐입니다.

`src/report/writers.js`의 네 writer(HTML, Markdown, DOCX, CSV)가 **같은 트리**를 렌더링합니다.
그래서 절을 하나 추가하면 네 포맷이 동시에 갖게 되고, 포맷 간에 내용이 어긋날 수 없습니다.

DOCX는 외부 라이브러리 없이 만듭니다 — `src/lib/zip.js`의 store 방식 ZIP 작성기와
최소 OOXML 파트 5개면 Word·LibreOffice·Google Docs가 모두 엽니다.

## 6. 창과 테마

### 프레임 없는 창

`frame: false`로 OS 제목 표시줄을 없애고 앱이 직접 그립니다.

- **메뉴 바**가 제목 표시줄을 겸합니다 (`-webkit-app-region: drag`)
- 프로그램 정보와 최소/최대/닫기는 **그 제목 표시줄 오른쪽 끝**
- 최대화 상태는 메인 프로세스가 `win:maximized` 이벤트로 알려 줍니다
  (더블클릭·Win+Up 등 앱을 거치지 않는 경로가 있기 때문)

### 대화상자는 진짜 창

Electron에서 팝업은 **별도의 `BrowserWindow`** 입니다. 페이지 안의 오버레이는
앱 창 밖으로 끌어낼 수 없는데, 설정 패널은 바로 그렇게 쓰고 싶은 물건이기 때문입니다.

같은 번들이 두 역할을 합니다 — URL에 `#dialog=<name>`이 있으면 `main.jsx`가
`App` 대신 `DialogHost`를 띄우고, 그 창은 해당 대화상자 하나만 그립니다.
`AppDialog`는 `standalone`일 때 배경막과 자체 드래그를 버리고 창을 가득 채웁니다
(OS 창이 이미 그 일을 하므로).

- **비모달 자식 창**입니다. 모달이면 옆으로 치워 둘 수 없고, 자식이라 앱 창 앞에 머뭅니다.
- **별도의 프로그램은 아닙니다.** 앱 창의 `close`에서 `closeAllDialogWindows()`를 불러
  함께 닫습니다.
- 결과는 `dialog:submit` → 메인 프로세스 → 열었던 창의 `dialog:result`로 돌아옵니다.
  보고서·다이어그램 내보내기는 **선택만 돌려주고**, 분석 결과를 쥔 창이 실제 저장을 합니다.
- 테마·언어는 `dialog:broadcastAppearance`로 열려 있는 모든 팝업 창에 전달됩니다.

웹 판에는 만들 창이 없으므로 `AppDialog`가 페이지 안에서 그대로 동작합니다
(끌어서 이동, 손잡이로 크기 조절, `autoFit`).

### 테마

색은 눈으로만 고르지 않고 **명암비로 검증**합니다. 찾아보기 버튼은 테마마다 다른 보조
강조색(`--accent-alt`)을 쓰는데, 처음에는 호버를 `filter: brightness()`로 처리했다가
**글자까지 함께 밝아져 라벨이 사라지는** 문제가 있었습니다. 지금은 테마마다
`--accent-alt-hover`를 따로 두고, 스모크가 6개 테마 × 2개 상태의 WCAG 명암비를 계산해
전부 AA(4.5:1) 이상인지 확인합니다. 그 과정에서 노르드(4.41)와 솔라라이즈드(4.21)의
기본 색이 이미 기준 미달이던 것도 드러나 함께 고쳤습니다.

테마는 CSS 커스텀 속성 토큰 맵입니다. `applyTheme(id)`가 `:root`에 얹으면
UI·다이어그램·내보낸 HTML 보고서가 한꺼번에 바뀝니다.
컴포넌트는 어떤 테마가 켜져 있는지 알 필요가 없습니다.

테마 선택은 **설정 창이 아니라 툴바**에 있습니다. 눈으로 보고 고르는 설정이므로
"적용" 단계를 두면 고르는 행위와 결과가 분리되기 때문입니다. 팔레트 버튼은 다음 테마로
순환하고, 화살표는 목록을 엽니다 — 어느 쪽이든 누르는 즉시 반영됩니다.

두 동작 모두 `settings.theme`를 클로저에서 읽지 않고 **함수형 업데이트**로 바꿉니다.
빠르게 세 번 누르면 React가 한 배치로 묶는데, 클로저를 읽으면 세 번 모두 같은 "다음 테마"를
계산해 한 칸만 이동하게 됩니다. 파일 저장은 순수해야 할 업데이터 밖(이펙트)에서 합니다.

SVG 내보내기만 예외입니다 — 문서 밖으로 나가면 `var()`가 풀리지 않으므로
`serializeSvg()`가 모든 토큰을 **실제 색상 값으로 구워 넣습니다.**

### 확대·축소 상태 보존

새 뷰를 처음 맞출 때는 **가로 가운데, 세로 상단**에 둡니다. 세로 가운데 정렬은
그래프의 뿌리를 캔버스 한복판으로 밀어내 눈이 찾아다니게 만듭니다.

그 뒤로는 두 가지를 각각 다른 장치로 지킵니다.

- **접기·펼치기**: `DiagramCanvas`는 `fitKey`가 바뀔 때만 화면에 맞춥니다.
  노드를 펼치면 그림 크기는 바뀌지만 `fitKey`는 그대로이므로 확대·축소가 유지됩니다.
- **뷰 전환**: 뷰마다 자기 `DiagramCanvas`를 마운트하므로 컴포넌트 상태로는 남지 않습니다.
  그래서 변환값을 모듈 수준의 `diagramTransforms` 맵에 `storageKey`(뷰마다 고정)로 저장하고,
  돌아왔을 때 그대로 복원합니다. 뷰마다 별도로 기억하므로 호출 그래프와 ERD가 서로 다른
  배율을 가질 수 있습니다. 새 분석 결과가 오면 `resetDiagramTransforms()`로 지웁니다.

### 렌더 오류는 흰 화면이 아니다

`src/components/ErrorBoundary.jsx`가 앱과 대화상자 창을 모두 감쌉니다.
렌더 중 예외가 나면 React가 트리를 통째로 언마운트해 **흰 창**만 남는데,
그건 사용자에게도 우리에게도 아무 정보를 주지 않습니다.
대신 오류 메시지·스택·컴포넌트 스택과 `다시 시도`·`새로 고침`·`오류 복사`를 보여 줍니다.

관련해서 지켜야 할 규칙이 하나 있습니다 — **상태 업데이터 안에서 ref를 읽지 말 것.**
다이어그램 팬이 `setView(prev => ({ ...prev, x: drag.current.originX + dx }))`처럼
업데이터 안에서 `drag.current`를 읽고 있었는데, React는 그 업데이터를 나중에(또는 두 번)
실행할 수 있고 그때는 `pointerup`이 이미 ref를 비운 뒤라 `null.originX`로 터졌습니다.
값은 이벤트 핸들러에서 **스냅샷으로 떠서** 넘기고, 저장 같은 부수 효과는 이펙트에서 합니다.

### 프로그래밍 언어 자동 감지

디렉터리 스캔은 **항상 모든 확장자**를 세고, 디렉터리마다 `extensionCounts`를 돌려줍니다.
선택된 언어로 스캔 범위를 좁히면 감지가 순환 논리가 됩니다 — 이미 고른 것만 발견하게 되니까요.

감지는 스캔이 아니라 **디렉터리 선택**을 따라갑니다. `[directories, checkedDirs]`에 걸린
이펙트가 체크된 디렉터리의 확장자 합계로 언어를 계산하므로, 폴더를 하나 체크하면 그
언어가 함께 들어오고 해제하면 빠집니다.
단 `languageSelectionCustomized`가 켜져 있으면(사용자가 직접 체크를 바꿨으면) 건드리지 않습니다.

빈 언어 목록은 **"아무것도 분석하지 않음"** 입니다. 예전에는 빈 목록이 분석기에서
"모든 언어"로 해석되어, 화면의 "전체 해제"가 실제로는 "전체 선택"과 같은 뜻이었습니다.
지금은 목록이 선택 그대로를 뜻하고, 비면 실행 버튼이 잠깁니다.

### 툴바는 라벨을 버리지 않는다

좁은 창에서 라벨을 숨기면 버튼이 무엇인지 알 수 없게 됩니다. 그래서 반대로 했습니다 —
스모크가 **툴바가 실제로 필요로 하는 폭**(모든 항목의 자연 너비 + 검색·여백의 최소값)을
재고, 창의 `minWidth`(`electron/ipc.js`의 `MIN_WINDOW_WIDTH`)가 그보다 크도록 강제합니다.
측정값 1041px에 영어 라벨과 다른 UI 폰트를 위한 여유를 더해 1160px로 두었습니다.

### 진행률 창

메인 스레드를 오래 잡는 두 가지에 각각 붙습니다.

- **분석**: 0.7초를 넘기면 뜹니다(짧은 분석에서 창이 깜박이지 않도록). 실제 백분율과 취소 버튼.
- **뷰 전환**: React 커밋은 동기이므로, 무거운 렌더를 **커밋하기 전 프레임에** 오버레이를 그려야
  합니다. `requestView()`가 중첩 `requestAnimationFrame`으로 그 순서를 만듭니다.
  얼마나 무거운지는 `viewCost()`가 결과 크기로 어림잡습니다 — 정확할 필요는 없지만
  자릿수가 틀리면 쓸데없이 창이 뜨거나, 설명 없이 화면이 멈춥니다.

`npm run smoke`는 별도입니다 — 실제 Electron으로 `dist/`를 띄우고
**메인 프로세스의 진짜 IPC 핸들러**(`electron/ipc.js`)를 등록한 뒤,
이 프로젝트의 `src/` 트리를 실제로 분석해 22가지를 확인합니다.

검사 항목(총 27가지): 메뉴·툴바 아이콘과 툴팁, 툴바 한 줄 배치, 제목 표시줄의 창 버튼과
정보 버튼, 디렉터리 스캔, 분석 완료, Summary 렌더링, 다이어그램 6종과 표 3종의 실제 내용,
**확대 상태가 접기·펼치기를 견디는지**, **뷰를 오갔다 돌아와도 뷰별 배율이 복원되는지**,
설정 창의 아이콘 제목·이동·크기 조절·스크롤 없음, **테마가 누를 때마다 실제로 바뀌는지**,
언어 전환, 컨텍스트 메뉴, 두 진행률 창의 실제 등장, 콘솔 오류 0.

대상은 이 저장소의 `CodeFactoryWinV10/CodeAnalyzer`(C# 약 47K LOC, 270파일)를 우선 사용합니다 —
진행률 창이 실제로 뜰 만큼 큰 코드베이스라야 그 기능을 검증할 수 있기 때문입니다.
없으면 이 프로젝트의 `src/`로 대체하고, 크기에 의존하는 검사는 건너뜁니다.

단위 테스트가 닿지 못하는 **어댑터 → IPC → 워커 → 뷰 → 내보내기 배선**을 덮는 것이 목적입니다.

**뷰별 레이아웃 감사**도 포함합니다 — 15개 뷰 전부를 **넓은 창(1500px)과 최소 창(1024px)**
두 폭에서 열어 다음을 확인합니다: 크래시 화면 없음, 뷰 본문 비어 있지 않음, 페이지가
가로·세로로 밀려나지 않음, 툴바가 한 줄이며 잘리지 않음, 모든 박스의 기하값이 유한,
다이어그램 viewBox가 정상이고 캔버스 안에 보이며 클리핑됨, 표 헤더와 본문의 열 수 일치,
패널·카드가 찌그러지지 않음.

> 이 감사를 쓸 때 주의할 점: 프로브 코드는 템플릿 리터럴로 렌더러에 전달되므로
> **`\\s`·`\\d` 같은 이스케이프가 백슬래시를 잃습니다.** 정규식을 쓰면 조용히 아무것도
> 매칭하지 않고 "모든 뷰가 깨졌다"는 거짓 보고가 나옵니다. 프로브 안에서는 정규식 대신
> `split(' ')` 같은 방법을 쓰세요.

## 8. 성능 한계

대형 저장소에서 메모리·시간이 폭주하지 않도록 상한을 둡니다.

| 대상 | 상한 |
|------|------|
| 파일 크기 | 2 MB (초과 시 건너뛰고 이유 기록) |
| 중복 검사 파일 수 | 2,500 |
| 중복 윈도우 맵 | 200,000 항목 |
| 중복 블록 길이 | 300줄 |
| 호출 그래프 트리 노드 | 1,200 |
| 시퀀스 메시지 | 300 (페이지당 60) |
| 표 행 | 3,000 (표시 개수 안내) |
| 순환 탐지 | 200개 사이클 |

파일 읽기는 60개씩 배치로 워커에 넘겨, 대형 프로젝트에서도 진행률이 계속 갱신됩니다.
분석이 끝나면 워커가 소스 텍스트를 즉시 버리고, 결과 객체에도 함수 본문을 담지 않습니다
(그래야 저장한 JSON이 몇 배로 커지지 않습니다).
