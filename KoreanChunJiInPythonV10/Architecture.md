# 설계 문서

## 출발점

이 저장소는 [KoreanChunJiInC++](../KoreanChunJiInC++) 의 조합 규칙을 파이썬으로
옮긴 것입니다. 바로 앞선 판인 [KoreanChunJiInRustV10](../KoreanChunJiInRustV10) 과
같은 얼개를 지키되, 말과 화면 라이브러리가 바뀌었습니다.

원본은 Windows 전용이고 Win32 API 위에 붙어 있었습니다. 목표는 두 가지입니다.

1. **조합 결과가 원본과 한 글자도 다르지 않을 것**
2. Windows · macOS · Linux · 웹 네 곳에서 돌 것

그래서 조합 엔진과 화면을 완전히 갈라 놓았습니다.
엔진은 운영체제를 하나도 모르고, 화면은 조합 규칙을 하나도 모릅니다.

## 계층

```
┌──────────────────────────────────────────────────────────┐
│ 데스크톱                        웹                        │
│ chunjiin/ui  (PySide6)          web/ (HTML · CSS · JS)   │
│   창 · 메뉴 · 툴바 · 키패드       화면 · 키패드              │
│   테마 4종 · 언어 2종             테마 4종 · 언어 2종         │
├──────────────────────────────────────────────────────────┤
│ chunjiin/__main__.py            chunjiin/web/server.py   │
│   (실행 파일)                     (엔진을 HTTP 로 내보냄)    │
├──────────────────────────────────────────────────────────┤
│ chunjiin/engine  순수 파이썬 · 표준 라이브러리만            │
│   chunjiin.py   원본 chunjiin.c  - 유니코드 조합, 겹받침     │
│   input.py      원본 input.c     - 오토마타, 편집 API        │
│   labels.py     라벨 · 모드 이름 · 상태줄                    │
└──────────────────────────────────────────────────────────┘
```

같은 `chunjiin.engine` 이 데스크톱 앱에도, 웹 서버에도 들어갑니다.
그래서 웹에서 친 "안녕" 과 데스크톱에서 친 "안녕" 이 다를 수가 없습니다.

## C++ · Rust 판과의 대응

| C++ | Rust | Python | 옮기면서 달라진 것 |
|---|---|---|---|
| `wchar_t text_buffer[4096]` | `Vec<char>` | `list[str]` | 널 종료 대신 길이. 최대 글자 수는 4095 로 같다 |
| `wchar_t chosung[4]` | `&'static str` | `str` | 낱자는 정적 표에서만 나온다 |
| `wchar_to_utf8()` | `State::text()` | `State.text()` | 파이썬 문자열은 이미 유니코드라 변환이 없다 |
| `get_unicode()` 의 if 사슬 | 표 + `index_of()` | 표 + `.index()` | 결과는 같다. 사슬 끝 기본값(ㅎ/ㅣ/ㅎ)도 그대로 둔다 |
| `check_double()` 의 if 사슬 | `[(&str, &str, &str); 11]` | 튜플 11줄 | 열한 줄짜리 표라 훑는 편이 해시보다 싸다 |
| `chunjiin_process_input()` | `State::key(i32)` | `State.key(int)` | |
| `HKCU\Software\Chunjiin` | `settings.json` | `settings.json` | 자리와 칸 이름이 Rust 판과 같다 |
| `IShellLinkW` 바로 가기 | PowerShell | PowerShell | COM 의존을 줄인다 |
| `RegSetValueEx` | `reg.exe` | `reg.exe` | 값이 몇 개뿐이라 꾸러미를 들이지 않는다 |
| Win32 `BS_OWNERDRAW` | egui 직접 그리기 | `QPainter` 직접 그리기 | 역할마다 색이 달라야 한다 |
| — | WASM | HTTP 서버 | 파이썬은 브라우저에서 돌지 않는다 |
| `go:embed` / `include_bytes!` | `build.rs` | PyInstaller `--add-data` | 빌드할 때 자산을 넣는다 |

### Rust 판과 값이 같아야 하는 것들

설정 파일(`settings.json`)의 칸 이름과 값의 뜻을 Rust 판과 똑같이 두었습니다.
테마 번호 · 글꼴 크기 · 연타 시간 · 시작 모드 · 언어 코드가 모두 같으므로,
두 판을 번갈아 써도 설정이 그대로 이어집니다.

색표(`PALETTES`)와 사용법 본문(`HELP_KO` / `HELP_EN`)도 Rust 판에서 글자
그대로 옮겼습니다. 사용법은 자판 그림과 모음 조합표의 칸이 맞아야 하므로
손으로 다시 치지 않고 원본 파일에서 잘라 붙였습니다.

### 원본의 함정을 그대로 둔 곳

`get_unicode()` 는 초성이 비어 있으면 `cho` 를 `18`(=`ㅎ`)로 떨어뜨립니다.
그래서 **초성이 없는 상태에서는 종성을 채우면 안 됩니다.**
오토마타는 모음만 있는 상태에서 자음을 받으면 앞 글자를 확정하고
새 음절의 초성으로 넣습니다(`ㅏ` + `ㄱ` → `ㅏㄱ` 두 글자).
파이썬 판도 이 규칙을 그대로 지킵니다. 고치면 결과가 원본과 달라집니다.

## 상태

```python
@dataclass
class StateBase:
    hangul: HangulState        # 조합 중인 한 음절
    now_mode: InputMode
    engnum: str | None         # 영문/숫자/기호 모드에서 조합 중인 문자
    text_buffer: list          # 글자 하나씩
    cursor_pos: int            # 삽입 위치

    # 아래는 원본 chunjiin.c 가 쓰지 않는 확장 필드
    last_key: int              # 직전에 눌린 키, 없으면 -1
    tap_count: int             # 같은 키 연타 위치
    compose_len: int           # 조합 글자가 차지한 칸 수 (0~2)
    prev_syllable: HangulState # 겹받침 되돌려 붙이기용
    prev_mergeable: bool
```

### 클래스를 셋으로 나눈 까닭

원본이 세 파일로 나뉘어 있으므로 클래스도 그 차례로 잇습니다.

```
chunjiin.py  StateBase    버퍼 · 유니코드 조합 · 초기화
input.py     StateInput   오토마타 · 편집 API
labels.py    State        라벨 · 모드 이름 · 상태줄
```

Rust 는 `impl State` 를 여러 파일에 나눠 적을 수 있지만 파이썬은 그럴 수
없습니다. 그래서 상속으로 잇습니다. 쓰는 쪽은 맨 끝의 `State` 하나만
보면 됩니다(`from chunjiin.engine import State`).

### 낱자를 문자열로 든 까닭

낱자는 `CONS_CYCLE`, `VOWEL_RULES`, `DOUBLE_JONG` 같은 정적 표에서만
나옵니다. 파이썬 문자열은 불변이므로 표에서 꺼내 넣기만 하면 됩니다.

다만 `HangulState` 는 **가변 객체**입니다. Rust 판은 `Copy` 라서 대입이
곧 복사였지만 파이썬은 참조입니다. 겹받침 되돌리기에서 앞 음절을 그대로
대입하면 두 이름이 한 몸이 되어, 뒤엣것을 고치는 순간 앞엣것까지 바뀝니다.
그래서 그 자리마다 `.copy()` 를 씁니다. `tests/test_engine.py` 의
`겹받침 되돌리기` 항목이 이것을 지킵니다.

### 조합 중인 글자를 화면에 두는 방법

조합 중인 글자는 **`cursor_pos` 바로 앞의 `compose_len` 칸**에 놓입니다.

```
text_buffer : 안 녕 하 세 요 ㄱ ·
                                 ^ cursor_pos
                           └──┬──┘
                        compose_len = 2
```

`_write_hangul()` 은 매번 그 칸들을 지우고 새로 그립니다.
음절이 확정되면 `compose_len` 을 0 으로 만듭니다. 그러면 이미 찍힌 칸이
그대로 확정 글자가 되고, 다음 글자는 새 칸에 들어갑니다.
따로 "확정 버퍼" 와 "조합 버퍼" 를 나눌 필요가 없습니다.

### 겹받침 되돌려 붙이기

받침 뒤에 온 자음이 겹받침을 이루지 못하면 새 음절로 떨어져 나갑니다.
그런데 자음 키는 순환하므로, **한 번 더 누르면 겹받침이 되는 자음이 나올 수
있습니다.**

```
만 + ㅅㅎ 키   ->  만ㅅ      (ㄴ+ㅅ 은 겹받침이 아니다)
     ㅅㅎ 키   ->  많        (ㄴ+ㅎ 은 ㄶ 이므로 도로 합친다)
```

이걸 위해 `State` 가 직전 음절을 `prev_syllable` 에 들고 있습니다.
`_try_merge_jong()` 이 순환 후보 중에 앞 음절의 받침과 합쳐지는 것을 찾으면,
`compose_len` 을 하나 늘려 **앞 칸까지 조합 영역으로 끌어들인 뒤** 다시 그립니다.
두 칸이 한 칸이 됩니다.

이 장치가 없으면 `ㄶ ㄻ ㄾ ㅀ` 이 들어간 글자(`많 삶 핥 옳`)를 아예 입력할 수
없습니다. 순환 첫 자리(`ㅅ ㅇ ㄷ`)가 겹받침을 못 이루기 때문입니다.

`prev_mergeable` 은 모음 · 문장부호 · 확정 · 백스페이스 · 커서 이동이 오면
바로 꺼집니다. 직전 키를 한 번 더 누른 경우에만 살아 있습니다.

### 아래아 중간 상태

`get_unicode()` 는 중성이 `·` 나 `‥` 이면 `None` 을 돌려줍니다(아직 모음이
아니므로). 그대로 두면 아래아를 누르는 동안 화면에 아무것도 안 보입니다.
그래서 `compose_display()` 가 그 경우만 따로 처리합니다.

```
초성 없음 + ·   →  "·"        (1칸)
초성 ㄱ  + ·    →  "ㄱ·"      (2칸)
초성 ㄱ  + ‥    →  "ㄱ‥"      (2칸)
```

초성만 있을 때의 호환 자모(`ㄱ`)를 얻으려고 중성을 비운 사본을 만들어
`get_unicode()` 를 부릅니다.

## 오토마타

### 모음

`VOWEL_RULES` 는 (현재 중성, 누른 키) → 다음 중성 전이표입니다.
`NO_VOWEL`(`"-"`)이면 그 조합은 없으므로 앞 글자를 확정하고 새 음절을 시작합니다.
마지막 칸은 백스페이스로 한 단계 되돌릴 때 씁니다.

```python
#  from     ㅣ        아래아     ㅡ        prev
("",     "ㅣ",     "·",      "ㅡ",     ""),
("·",    "ㅓ",     "‥",      "ㅗ",     ""),
("ㅗ",   "ㅚ",     "ㅛ",     NO_VOWEL, "·"),
("ㅚ",   NO_VOWEL, "ㅘ",     NO_VOWEL, "ㅗ"),
```

`ㅝ` 는 `ㅠ` + `ㅣ` 로 들어옵니다. `ㅠㅣ` 라는 모음이 없기 때문에
그 자리를 `ㅝ` 로 쓰는 것이 천지인의 규칙입니다.

표는 줄로 적어 두고 `_VOWEL_BY_FROM` 이 현재 중성으로 바로 찾을 수 있게
풀어 둡니다. 표 모양은 원본과 눈으로 대조할 수 있게 그대로 남겨 둡니다.

### 자음

`CONS_CYCLE` 은 키마다 순환 목록을 갖습니다(`ㄱ ㅋ ㄲ`).
같은 키가 연달아 오면 순환하고, 그렇지 않으면 자리(초성 → 종성 → 겹받침)를
채웁니다.

순환 대상이 종성이면 `is_valid_jong()` 으로 걸러서 `ㄸ ㅃ ㅉ` 이 받침에
들어가지 않게 하고, 겹받침 자리면 `check_double()` 로 실제로 합쳐지는지
확인합니다.

### 연음

받침이 있는 상태에서 모음 키가 오면, 마지막 자음을 떼어 새 음절의 초성으로
옮깁니다.

```
간(ㄱ ㅏ ㄴ) + ㅏ
  → 받침 ㄴ 을 떼고 "가" 확정
  → 새 음절 초성 ㄴ + 모음 ㅏ = "나"
```

겹받침이면 두 번째 자음만 넘어갑니다(`값` + 모음 → `갑` + `사...`).

### 연타 순환을 끊는 시점

`안녕` 처럼 같은 키가 연달아 필요할 때를 위해 `break_multitap()` 이
`last_key` 를 지웁니다. 화면 쪽이 두 곳에서 부릅니다.

- 키 입력 뒤 정해 둔 시간(기본 0.8초)
- 커서 이동 · 확정 계열 동작 (`→`, `←`, `Esc`, 스페이스 등은 `commit()` 이 겸함)

데스크톱은 `QTimer` 하나를 다시 잽니다. 웹은 `setTimeout` 입니다.
둘 다 엔진에는 시계가 없습니다. 엔진은 언제 끊을지 모르고, 끊으라고
하면 끊을 뿐입니다.

## 데스크톱 화면 (chunjiin/ui)

### 엔진이 원본, 화면은 거울

화면은 조합 상태를 하나도 들고 있지 않습니다. 무엇을 하든 마지막에
`refresh()` 하나만 부르면 화면이 엔진과 같아집니다. 그래서 어긋날
자리가 없습니다.

`refresh()` 는 편집칸의 글과 커서, 12키의 라벨과 색, 상태줄, 모드 표시를
한꺼번에 엔진에서 읽어 옮깁니다.

### 편집 영역

Qt 의 `QPlainTextEdit` 을 쓰되 **직접 타이핑하지 못하게** 막습니다.

- `keyPressEvent` 를 가로채 엔진으로 돌립니다.
- `inputMethodEvent` 를 삼킵니다. 그러지 않으면 운영체제의 한글 IME 가
  끼어들어 우리 엔진과 두 겹으로 조합합니다.
- `insertFromMimeData` 로 들어오는 붙여넣기도 엔진을 거칩니다.
- 찍은 자리(`mouseReleaseEvent`)만 엔진 커서로 되돌립니다.

읽기 전용(`setReadOnly`)으로 두지 않는 까닭은, 그렇게 하면 Qt 가 깜박이는
막대를 감추기 때문입니다. 편집은 열어 두고 이벤트를 우리가 먼저 받습니다.
C++ 판이 읽기 전용 `EDIT` 컨트롤을 서브클래스해서 하던 일과 같습니다.

### 물리 키보드를 창 어디서든 받기

키패드 버튼을 누르면 초점이 그리로 갈 수 있습니다. 그러면 키가 편집칸에
닿지 않습니다. 두 가지로 막습니다.

- 직접 그리는 버튼은 `FocusPolicy.NoFocus` 라 초점을 받지 않습니다.
- 그래도 새는 경우를 위해 `QApplication` 에 이벤트 필터를 걸어
  창이 활성일 때의 키를 우리가 먼저 봅니다. 대화 상자가 떠 있으면 그쪽이
  먼저입니다.

### 버튼

키패드 버튼과 툴바 버튼은 Qt 기본 단추를 쓰지 않고 직접 그립니다.
역할(자음 / 모음 / 문장부호 / 기능 / 모드 / 툴바)마다 색이 달라야 하는데,
스타일시트로 버튼마다 다른 색을 주려면 위젯 수만큼 시트를 만들어야 하고
테마를 바꿀 때마다 다시 붙여야 합니다. 직접 그리면 팔레트만 갈아 끼우면
됩니다. C++ 판이 `BS_OWNERDRAW` 로 하던 일과 같습니다.

자리는 `layout.py` 가 미리 셈해서 알려 줍니다. 그 셈은 화면을 하나도
건드리지 않는 순수한 계산이라 창 없이 시험할 수 있습니다.

### 창 폭과 툴바

창의 최소 폭은 **툴바가 정합니다.** 툴바 열한 칸이 다 보이는 가장 좁은
폭을 셈해서(`TOOLBAR_MIN_W`) 그것을 창의 최소 폭이자 처음 폭으로 씁니다.
버튼 수나 크기를 고치면 창 폭이 저절로 따라갑니다.

창 관리자가 최소 크기를 지키지 않는 일이 있습니다. 그때는 **버튼을
줄여서라도 열한 칸을 모두 보입니다.** 몇 개를 잘라 내는 것보다 작게라도
다 보이는 편이 낫습니다. `툴바가 잘리지 않는다` 시험이 아주 좁은 폭까지
훑어 겹치거나 판 밖으로 나가는 칸이 없는지 봅니다.

### 그림

Qt 에는 우리가 쓸 아이콘 꾸러미가 없으므로 같은 모양을 선으로 직접
그립니다(`icons.py`). 좌표는 웹 판과 같은 24x24 자리에 적어 두어 두 판의
그림이 같습니다.

이모지를 쓰면 시스템마다 색과 크기가 달라지고, 글꼴 문자 `↵`(U+21B5) 와
`⌫`(U+232B) 는 함께 넣은 Noto Sans KR 에 없어서 빈칸이 됩니다. 그래서 그
두 자리는 반드시 그림이어야 합니다. `↵ ⌫ 는 그림` 시험이 이것을 지킵니다.

좌표를 점 목록으로 푸는 일(`icon_polylines`)은 Qt 를 하나도 쓰지 않는
순수한 계산이라 화면 없이 시험할 수 있습니다.

### 글꼴

시스템 한글 글꼴에 기대지 않고 **Noto Sans KR 을 함께 배포합니다.**
완성형 11172자를 모두 담고 있어야 `갂 갃` 같은 글자도 그려집니다.
글꼴이 없는 컴퓨터에서도 화면이 같아집니다.

가변 글꼴 `NotoSansKR[wght].ttf` 를 그대로 넣으면 안 됩니다.
그 글꼴은 `wght` 축의 **기본값이 100(Thin)** 이라서 글자가 아주 가늘게,
흐릿하게 나옵니다. 그래서 400 과 700 으로 미리 뽑아 둔 두 벌을 넣습니다.

**글꼴 등록은 첫 창을 만들기 전에 끝나야 합니다.** `QApplication` 을 만든
뒤라야 글꼴 데이터베이스가 열리므로, 앱을 만드는 길을 `run()` 하나로
좁히고 거기서 등록합니다.

### 테마

색은 모두 `PALETTES` 표에서 가져옵니다. C++ 판 `THEMES[]` · Rust 판
`PALETTES` 와 같은 값입니다. 창 배경 · 카드 · 테두리 · 글자 · 흐린 글자와,
버튼 역할마다 다섯 가지 색(기본 · 호버 · 눌림 · 테두리 · 글자)을 갖습니다.

`stylesheet_for()` 는 팔레트만으로 Qt 가 그리는 모든 색을 냅니다.
정하지 않고 Qt 기본값에 맡기는 자리를 두지 않습니다. 그렇게 두면
운영체제의 밝기 설정이 우리 팔레트를 뒤엎어, 어떤 테마에서 글자가
배경에 묻힙니다.

### 언어

`Strings` 라는 `dataclass` 하나에 화면에 나오는 모든 글자가 들어 있습니다.
칸이 정해져 있으므로 **항목을 하나 빠뜨리면 만들 때 바로 터집니다.**
`언어표` 시험이 두 언어의 모든 칸이 비지 않았는지 전수로 봅니다.

### 딸린 창

사용법 · 정보 · 설정은 진짜 창으로 띄웁니다(C++ 판도 그랬습니다).
세 창 모두 **스크롤 막대가 없고, 단추 아래에 빈 자리가 남지 않습니다.**
크기를 못박지 않고 내용에 맞추기 때문입니다.

Rust 판(egui)은 곧바로 그리는 방식이라 창을 내용에 맞추려면 한 판 그려
보고 재야 했습니다. Qt 는 위젯이 스스로 알맞은 크기를 알려 주므로
(`sizeHint`) 그 장치가 여기서는 필요 없습니다. 배치자에 담기만 하면
됩니다.

사용법은 70줄입니다. 한 줄로 세우면 창이 화면보다 길어져 스크롤이
생깁니다. 그래서 `[ 제목 ]` 단위로 잘라 두 칸에 나눠 놓습니다
(`help.two_columns`). 구역 하나를 두 칸에 걸쳐 놓지는 않습니다.
읽는 차례가 끊기기 때문입니다.

### 설정

`Settings` 를 JSON 파일 하나로 저장합니다. **칸 이름과 값은 Rust 판과
같습니다.**

```
Windows  %AppData%\Chunjiin\settings.json
macOS    ~/Library/Application Support/Chunjiin/settings.json
Linux    ~/.config/Chunjiin/settings.json
```

경로를 만드는 함수는 갈아 끼울 수 있게 두었습니다(`set_settings_path`).
시험이 그것을 임시 폴더로 돌려세우기 위해서입니다. 환경 변수를 건드리는
것만으로는 운영체제마다 다른 설정 폴더를 확실히 돌려세울 수 없어, 실제
사용자 설정을 덮어쓸 위험이 있었습니다.

## 웹 화면 (web/)

### 엔진은 서버에

Rust 판은 엔진을 WASM 으로 만들어 브라우저 안에 넣었습니다.
**파이썬은 브라우저에서 돌지 않으므로 그 자리를 서버가 대신합니다.**

```
누름 → POST /api/key → 상태(JSON) → render(상태)
```

조합은 하나도 자바스크립트에서 하지 않습니다. 그래서 데스크톱 판과
결과가 어긋날 수 없다는 점은 Rust 판과 같습니다. 대신 오갈 것이 생겼으므로
두 가지를 챙깁니다.

- **차례를 지킵니다.** 누른 차례가 곧 조합 차례이므로 요청을 겹쳐 보내면
  안 됩니다. `app.js` 가 약속(Promise)을 한 줄로 이어 앞의 것이 끝난 뒤에
  다음을 보냅니다. 그래서 빨리 눌러도 글자가 뒤바뀌지 않습니다.
- **세션을 가릅니다.** 브라우저 탭 하나에 입력기 하나를 쿠키로 매답니다.
  여러 사람이 같은 서버에 붙어도 서로의 글이 섞이지 않습니다. 오래 쓰지
  않은 세션은 치웁니다.

상태 객체(`snapshot`)의 칸 이름은 Rust 판 WASM 이 내보내던 것과 같습니다.
그래서 `web/app.js` 의 그리는 쪽은 두 판에서 거의 같은 코드입니다.

### 화면

- 편집칸은 진짜 `<textarea>` 입니다. 그래야 브라우저가 커서 · 선택 · 스크롤을
  맡아 줍니다. `beforeinput` 을 막아 직접 편집은 못 하게 합니다.
- 글꼴은 내려받지 않고 시스템 한글 글꼴을 씁니다. 더 또렷하고, 6MB 짜리
  글꼴을 받게 하지 않아도 됩니다.
- 색은 CSS 변수로 두고 `<body data-theme="...">` 를 갈아 테마를 바꿉니다.
  값은 데스크톱 판 `PALETTES` 와 같습니다.
- 화면 설정은 `localStorage` 에 넣습니다(글 자체는 서버 세션에 있습니다).
- 툴바 아이콘은 인라인 SVG 입니다.

### 서버

`http.server` 하나로 정적 파일과 `/api/*` 를 함께 맡습니다. 하는 일이
"파일 내려 주기 + 상태 한 벌" 뿐이라 서버 꾸러미를 들이지 않습니다.

`..` 은 경로를 다듬을 때 없앱니다. 남겨 두면 서버 밖의 파일까지 내려 주게
됩니다. `경로 · 형식` 시험이 그것을 전수로 봅니다.

## 실행 파일에 무엇을 품는가

| 무엇 | 어디에 | 누가 넣나 |
|---|---|---|
| 글꼴 · 아이콘 | 앱 · 설치 프로그램 | `--add-data assets` |
| 웹 판 화면 | 서버 | `--add-data web` |
| 앱 실행 파일 | 설치 프로그램 | `--add-data dist/chunjiin` |

`scripts/pyinstaller_build.py` 한 곳에서 인자를 만들어 넘깁니다. `.spec`
파일을 저장소에 두지 않는 까닭은, 손으로 고칠 자리가 많아 셋(앱 · 서버 ·
설치 프로그램)이 어긋나기 쉽기 때문입니다.

### 한 파일이냐 한 폴더냐

**셋 다 한 파일로 만들어 저장소 루트에 둡니다.** 다른 판들과 같은
관례이고, 루트에 놓인 실행 파일 하나만 있으면 그대로 돌아야 하기
때문입니다.

한 파일 묶음은 뜰 때마다 자기를 임시 폴더에 풉니다. Qt 가 들어간 앱은
그것이 2~3초 걸립니다. 날마다 쓰면서 그것이 거슬리면 `--onedir` 로
만들어 `dist/chunjiin/` 을 폴더째 쓰면 곧바로 뜹니다.

그래서 `--copy-root` 는 **한 파일로 만든 것만** 루트에 놓습니다.
한 폴더 묶음은 실행 파일만 떼어 놓으면 딸린 파일이 없어 돌지 않으므로,
어디에 만들어졌는지만 알려 줍니다.

| | 한 파일 (기본) | 한 폴더 (`--onedir`) |
|---|---|---|
| 놓이는 곳 | 저장소 루트 | `dist/chunjiin/` |
| 옮길 때 | 파일 하나 | 폴더째 |
| 처음 뜨는 데 | 2~3초 | 곧바로 |
| 크기 | 앱 51MB · 서버 9MB | 앱 125MB · 서버 20MB |

갓 만들었거나 갓 설치한 직후 처음 한 번은 20초 넘게 걸릴 수 있습니다.
바이러스 검사가 새 파일을 통째로 훑기 때문입니다.

### 스크립트가 환경 변수를 세션에 남기면 안 된다

`test.ps1` 은 **지금 그 PowerShell 프로세스 안에서** 돕니다. 그래서
`$env:QT_QPA_PLATFORM = 'offscreen'` 을 그냥 두면 시험이 끝난 뒤에도 그
창에 남습니다. 그 상태로 앱을 띄우면 창이 뜨지 않고 Qt 가 이렇게만
나무랍니다.

```
QFontDatabase: Cannot find font directory .../PySide6/lib/fonts.
```

실제로 그렇게 헷갈렸습니다. 그래서 `test.ps1` · `package.ps1` 은 옛 값을
기억해 두었다가 `finally` 에서 반드시 되돌립니다. `.sh` 쪽은 스크립트가
제 프로세스에서 돌므로 그런 일이 없습니다.

### 글꼴 폴더를 알려 준다

Qt 는 더 이상 글꼴을 함께 배포하지 않습니다. 그래서 `offscreen` 처럼
운영체제 글꼴을 쓰지 않는 화면 갈래로 돌리면 위의 잔소리가 나옵니다.
우리는 Noto Sans KR 을 함께 배포하므로 `font.prepare()` 가
`QT_QPA_FONTDIR` 를 그 폴더로 가리킵니다. **`QApplication` 을 만들기
전에** 불러야 합니다.

### 진입점은 절대 임포트여야 한다

`chunjiin/__main__.py` · `chunjiin/web/__main__.py` ·
`chunjiin/setup/__main__.py` 는 임포트를 상대(`from .server import main`)로
적으면 안 됩니다. PyInstaller 가 이 파일들을 `__main__` 으로 돌리는데,
그때는 딸린 꾸러미가 없어서 `attempted relative import with no known parent
package` 로 죽습니다. `python -m` 으로 부를 때와 묶어 놓았을 때가 모두
돌려면 절대 임포트여야 합니다.

## 설치 프로그램

`chunjiin/setup` 은 C++ 판 `installer/setup.c` 와 같은 생각입니다.
앱을 자기 안에 품고 있다가 설치 폴더에 풉니다.
관리자 권한이 필요 없고, 다른 설치 도구를 깔지 않아도 됩니다.

- **Windows** — 앱을 놓고, PowerShell 의 `WScript.Shell` 로 시작 메뉴
  바로 가기를 만들고, `reg.exe` 로 `HKCU\...\Uninstall\Chunjiin` 에 등록
  정보를 씁니다. 레지스트리 꾸러미를 들이지 않는 까닭은 쓰는 값이 몇
  개뿐이고 `reg.exe` 가 Windows 에 늘 있기 때문입니다.
- **Linux** — `~/.local/share/Chunjiin` 에 놓고, `~/.local/bin` 에 링크를 걸고,
  `.desktop` 항목과 아이콘을 만듭니다.
- **macOS** — `~/Applications/Chunjiin.app` 묶음을 만듭니다.

### 자기 자신을 지우기

제거할 때는 제거기 자신이 그 폴더에서 돌고 있으므로 지금 지울 수 없습니다.
잠깐 기다렸다 지우는 배치 파일을 띄우고 물러납니다. 여기에 함정이 둘
있었습니다. 둘 다 실제로 겪은 것입니다.

**하나.** 기다리는 데 `timeout` 을 쓰면 안 됩니다. 그 명령은 콘솔에서
키를 읽으려 하므로 창 없이 띄운 프로세스에서는 곧바로 실패합니다.
콘솔이 없어도 도는 `ping` 으로 시간을 끕니다.

**둘.** 명령을 `cmd /C "..."` 한 줄로 넘기면 안 됩니다. 지울 폴더 경로에
띄어쓰기가 있으면 따옴표를 씌워야 하는데, 그것이 `/C` 를 감싼 따옴표와
겹쳐 cmd 가 엉뚱하게 끊어 읽습니다. 그래서 배치 파일에 적어 두고 그
파일을 부릅니다.

사용자 이름이 한글이면 설치 경로에도 한글이 들어갑니다. 배치 파일은
유니코드가 아니라 시스템 코드페이지로 읽히므로, 될 수 있으면 언제나
아스키인 8.3 짧은 이름으로 바꿔 적습니다.

### 모듈 이름이 `install.py` 가 아닌 까닭

그러면 꾸러미 안에서 모듈 `install` 과 함수 `install()` 이 같은 이름을
다툽니다. `__init__.py` 가 함수를 내보내는 순간 모듈이 가려져
`from . import install` 이 함수를 집어 옵니다. 실제로 그렇게 한 번
넘어져서 `installer.py` 로 두었습니다.

## 시험 얼개

```
tests/test_cases.py   C++ 원본에서 뽑아 온 430항목 (test/cases.tsv)
tests/test_engine.py  자료로 뽑을 수 없는 항목 - 영문 26자 전수,
                      라벨-입력 일치, 원본 함수 직접 확인, 경계·예외
tests/test_ui.py      색표 · 설정 · 배치 · 커서 변환 · 언어 · 그림,
                      그리고 창까지 만들어 보는 스모크 시험
tests/test_web.py     서버 경로 처리, 상태 객체, 실제로 띄워 두드려 보기
tests/test_setup.py   설치 자리와 만들어 내는 글
tests/test_report.py  보고기 자체 - 줄 풀기, 칸 맞추기, 색
tests/report.py       시험 실행기 겸 보고기
```

### 기대값을 손으로 옮겨 적지 않는다

조합 결과의 기대값은 `test/cases.tsv` 에 있습니다. 그 파일은 Rust 판이
C++ 원본의 `tests/test_engine.c` 에서 뽑아낸 것을 그대로 가져온 것입니다.
손으로 옮겨 적지 않으므로 원본이 고쳐지면 시험도 따라갑니다.

`자료 검사` 항목이 그 파일 자체가 성한지도 봅니다. 뽑아내는 쪽이 조용히
망가지면 시험이 통째로 비어도 통과해 버리기 때문입니다.

### pytest 를 깔지 않아도 된다

`tests/report.py` 가 `tests/test_*.py` 안의 `test_*` 함수를 찾아 부르고,
각 항목이 남긴 `@@CASE` 줄을 모아 구역별로 정리합니다. C++ 판
`test_engine` 이 보여 주던 구역별 집계와 전체 요약을 그대로 냅니다.

시험 함수는 항목마다 `check()` 로 한 줄을 남기고 **끝에서 한 번만**
`assert` 합니다. 그래야 첫 실패에서 멈추지 않고 어디가 몇 개 틀렸는지
다 볼 수 있습니다.

함수 차례는 파일에 적힌 순(코드 줄 번호)을 지킵니다. 구역이 원본에 나온
차례대로 보이게 하려는 것입니다.

### 결과를 눈으로 읽기 좋게

구역 이름과 숫자 칸이 세로로 맞고, 통과·실패가 색으로 갈립니다.

칸은 **글자 수가 아니라 눈에 보이는 폭**으로 맞춥니다. 한글은 터미널에서
두 칸을 차지하므로 `"{:<28}"` 같은 것으로 채우면 한글이 섞인 이름들이
세로로 어긋납니다. 폭은 묶음 전체를 한꺼번에 재므로 묶음이 달라도 숫자
열이 같은 자리에 섭니다. `tests/test_report.py` 가 실제로 찍어 보고
슬래시가 한 자리에 있는지 셉니다.

색은 화면으로 나갈 때만 켭니다. 파일이나 파이프로 흘려보낼 때 색 부호가
섞이면 읽기 나쁘기 때문입니다. 옛 Windows 콘솔은 색 부호를 켜 주어야
