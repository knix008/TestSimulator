# 설계 문서

## 출발점

이 저장소는 [KoreanChunJiInC++](../KoreanChunJiInC++) 의 조합 규칙을 Rust 로
옮긴 것입니다. 바로 앞선 판인 [KoreanChunjiInGoV10](../KoreanChunjiInGoV10) 과
같은 얼개를 지키되, 말과 화면 라이브러리가 바뀌었습니다.

원본은 Windows 전용이고 Win32 API 위에 붙어 있었습니다. 목표는 두 가지입니다.

1. **조합 결과가 원본과 한 글자도 다르지 않을 것**
2. Windows · macOS · Linux · 웹 네 곳에서 돌 것

그래서 조합 엔진과 화면을 완전히 갈라 놓았습니다.
엔진은 운영체제를 하나도 모르고, 화면은 조합 규칙을 하나도 모릅니다.

## 계층

```
┌──────────────────────────────────────────────────────────┐
│ 데스크톱                        웹                        │
│ crates/ui  (egui / eframe)      web/ (HTML · CSS · JS)   │
│   창 · 메뉴 · 툴바 · 키패드       화면 · 키패드              │
│   테마 4종 · 언어 2종             테마 4종 · 언어 2종         │
├──────────────────────────────────────────────────────────┤
│ crates/app                      crates/wasm              │
│   (실행 파일)                     (엔진을 JS 로 내보냄)      │
├──────────────────────────────────────────────────────────┤
│ crates/engine   순수 Rust · 의존성 0 · 운영체제를 모른다     │
│   chunjiin.rs   원본 chunjiin.c  - 유니코드 조합, 겹받침     │
│   input.rs      원본 input.c     - 오토마타, 편집 API        │
│   labels.rs     라벨 · 모드 이름 · 상태줄                    │
└──────────────────────────────────────────────────────────┘
```

같은 `chunjiin-engine` 이 데스크톱 실행 파일에도, WASM 에도 들어갑니다.
그래서 웹에서 친 "안녕" 과 데스크톱에서 친 "안녕" 이 다를 수가 없습니다.

## C++ · Go 판과의 대응

| C++ | Go | Rust | 옮기면서 달라진 것 |
|---|---|---|---|
| `wchar_t text_buffer[4096]` | `[]rune` | `Vec<char>` | 널 종료 대신 길이. 최대 글자 수는 4095 로 같다 |
| `wchar_t chosung[4]` | `string` | `&'static str` | 낱자는 정적 표에서만 나오므로 배분이 없다 |
| `wchar_to_utf8()` | `State.Text()` | `State::text()` | Rust 문자열은 이미 UTF-8 이라 변환이 필요 없다 |
| `get_unicode()` 의 if 사슬 | 표 + `indexOf()` | 표 + `index_of()` | 결과는 같다. 사슬 끝 기본값(ㅎ/ㅣ/ㅎ)도 그대로 둔다 |
| `check_double()` 의 if 사슬 | `map[string]map[string]string` | `[(&str, &str, &str); 11]` | 열한 줄짜리 표라 훑는 편이 해시보다 싸다 |
| `chunjiin_process_input()` | `State.Key(int)` | `State::key(i32)` | |
| `HKCU\Software\Chunjiin` | `settings.json` | `settings.json` | 자리와 칸 이름이 Go 판과 같다 |
| `IShellLinkW` 바로 가기 | PowerShell | PowerShell | COM 의존을 줄인다 |
| `RegSetValueEx` | `golang.org/x/sys` | `reg.exe` | 값이 여섯 개뿐이라 꾸러미를 들이지 않는다 |
| Fyne | Fyne | egui / eframe | C 컴파일러가 필요 없어졌다 |
| `go:embed` | `go:embed` | `build.rs` + `include_bytes!` | 빌드할 때 목록을 만들어 둔다 |

### Go 판과 값이 같아야 하는 것들

설정 파일(`settings.json`)의 칸 이름과 값의 뜻을 Go 판과 똑같이 두었습니다.
테마 번호 · 글꼴 크기 · 연타 시간 · 시작 모드 · 언어 코드가 모두 같으므로,
두 판을 번갈아 써도 설정이 그대로 이어집니다.

### 원본의 함정을 그대로 둔 곳

`get_unicode()` 는 초성이 비어 있으면 `cho` 를 `18`(=`ㅎ`)로 떨어뜨립니다.
그래서 **초성이 없는 상태에서는 종성을 채우면 안 됩니다.**
오토마타는 모음만 있는 상태에서 자음을 받으면 앞 글자를 확정하고
새 음절의 초성으로 넣습니다(`ㅏ` + `ㄱ` → `ㅏㄱ` 두 글자).
Rust 판도 이 규칙을 그대로 지킵니다. 고치면 결과가 원본과 달라집니다.

## 상태

```rust
pub struct State {
    pub hangul: HangulState,   // 조합 중인 한 음절
    pub now_mode: InputMode,
    pub engnum: Option<char>,  // 영문/숫자/기호 모드에서 조합 중인 문자
    pub text_buffer: Vec<char>,
    pub cursor_pos: usize,     // 삽입 위치

    // 아래는 원본 chunjiin.c 가 쓰지 않는 확장 필드
    pub last_key: i32,             // 직전에 눌린 키, 없으면 -1
    pub tap_count: usize,          // 같은 키 연타 위치
    pub compose_len: usize,        // 조합 글자가 차지한 칸 수 (0~2)
    pub prev_syllable: HangulState, // 겹받침 되돌려 붙이기용
    pub prev_mergeable: bool,
}
```

### 낱자를 `&'static str` 로 든 까닭

낱자는 `CONS_CYCLE`, `VOWEL_RULES`, `DOUBLE_JONG` 같은 정적 표에서만 나옵니다.
새로 만들어지는 문자열이 하나도 없으므로 빌려 쓰기만 하면 됩니다.
그래서 `HangulState` 가 `Copy` 가 되고, 겹받침 되돌리기에서 앞 음절을
통째로 복사해 두는 일이 값싸집니다.

### 조합 중인 글자를 화면에 두는 방법

조합 중인 글자는 **`cursor_pos` 바로 앞의 `compose_len` 칸**에 놓입니다.

```
text_buffer : 안 녕 하 세 요 ㄱ ·
                                 ^ cursor_pos
                           └──┬──┘
                        compose_len = 2
```

`write_hangul()` 은 매번 그 칸들을 지우고 새로 그립니다.
음절이 확정되면 `compose_len` 을 0 으로 만듭니다. 그러면 이미 찍힌 칸이
그대로 확정 글자가 되고, 다음 글자는 새 칸에 들어갑니다.
따로 "확정 버퍼" 와 "조합 버퍼" 를 나눌 필요가 없습니다.

### 겹받침 되돌려 붙이기

받침 뒤에 온 자음이 겹받침을 이루지 못하면 새 음절로 떨어져 나갑니다.
그런데 자음 키는 순환하므로, **한 번 더 누르면 겹받침이 되는 자음이 나올 수
있습니다.**

```
만 + ㅅㅎ 키   ->  만ㅅ      (ㄴ+ㅅ 은 겹받침이 아니다)
     ㅅㅎ 키   ->  많        (ㄴ+ㅎ 은 ㄶ 이므로 도로 합친다)
```

이걸 위해 `State` 가 직전 음절을 `prev_syllable` 에 들고 있습니다.
`try_merge_jong()` 이 순환 후보 중에 앞 음절의 받침과 합쳐지는 것을 찾으면,
`compose_len` 을 하나 늘려 **앞 칸까지 조합 영역으로 끌어들인 뒤** 다시 그립니다.
두 칸이 한 칸이 됩니다.

이 장치가 없으면 `ㄶ ㄻ ㄾ ㅀ` 이 들어간 글자(`많 삶 핥 옳`)를 아예 입력할 수
없습니다. 순환 첫 자리(`ㅅ ㅇ ㄷ`)가 겹받침을 못 이루기 때문입니다.

`prev_mergeable` 은 모음 · 문장부호 · 확정 · 백스페이스 · 커서 이동이 오면
바로 꺼집니다. 직전 키를 한 번 더 누른 경우에만 살아 있습니다.

### 아래아 중간 상태

`get_unicode()` 는 중성이 `·` 나 `‥` 이면 `None` 을 돌려줍니다(아직 모음이
아니므로). 그대로 두면 아래아를 누르는 동안 화면에 아무것도 안 보입니다.
그래서 `compose_display()` 가 그 경우만 따로 처리합니다.

```
초성 없음 + ·   →  "·"        (1칸)
초성 ㄱ  + ·    →  "ㄱ·"      (2칸)
초성 ㄱ  + ‥    →  "ㄱ‥"      (2칸)
```

초성만 있을 때의 호환 자모(`ㄱ`)를 얻으려고 중성을 비운 사본을 만들어
`get_unicode()` 를 부릅니다. Go 판은 원본을 잠깐 고쳤다 되돌렸는데,
`HangulState` 가 `Copy` 라서 사본을 뜨는 편이 더 싸고 안전합니다.

## 오토마타

### 모음

`VOWEL_RULES` 는 (현재 중성, 누른 키) → 다음 중성 전이표입니다.
`NO_VOWEL` 이면 그 조합은 없으므로 앞 글자를 확정하고 새 음절을 시작합니다.
`prev` 칸은 백스페이스로 한 단계 되돌릴 때 씁니다.

```rust
//             from      ㅣ         아래아     ㅡ         prev
VowelRule { from: "",   by_i: "ㅣ",     by_dot: "·",  by_eu: "ㅡ",     prev: ""   },
VowelRule { from: "·",  by_i: "ㅓ",     by_dot: "‥",  by_eu: "ㅗ",     prev: ""   },
VowelRule { from: "ㅗ", by_i: "ㅚ",     by_dot: "ㅛ", by_eu: NO_VOWEL, prev: "·"  },
VowelRule { from: "ㅚ", by_i: NO_VOWEL, by_dot: "ㅘ", by_eu: NO_VOWEL, prev: "ㅗ" },
```

`ㅝ` 는 `ㅠ` + `ㅣ` 로 들어옵니다. `ㅠㅣ` 라는 모음이 없기 때문에
그 자리를 `ㅝ` 로 쓰는 것이 천지인의 규칙입니다.

### 자음

`CONS_CYCLE` 은 키마다 순환 목록을 갖습니다(`ㄱ ㅋ ㄲ`).
같은 키가 연달아 오면 순환하고, 그렇지 않으면 자리(초성 → 종성 → 겹받침)를
채웁니다.

순환 대상이 종성이면 `is_valid_jong()` 으로 걸러서 `ㄸ ㅃ ㅉ` 이 받침에
들어가지 않게 하고, 겹받침 자리면 `check_double()` 로 실제로 합쳐지는지
확인합니다.

### 연음

받침이 있는 상태에서 모음 키가 오면, 마지막 자음을 떼어 새 음절의 초성으로
옮깁니다.

```
간(ㄱ ㅏ ㄴ) + ㅏ
  → 받침 ㄴ 을 떼고 "가" 확정
  → 새 음절 초성 ㄴ + 모음 ㅏ = "나"
```

겹받침이면 두 번째 자음만 넘어갑니다(`값` + 모음 → `갑` + `사...`).

### 연타 순환을 끊는 시점

`안녕` 처럼 같은 키가 연달아 필요할 때를 위해 `break_multitap()` 이
`last_key` 를 지웁니다. 화면 쪽이 두 곳에서 부릅니다.

- 키 입력 뒤 정해 둔 시간(기본 0.8초)
- 커서 이동 · 확정 계열 동작 (`→`, `←`, `Esc`, 스페이스 등은 `commit()` 이 겸함)

Go 판은 시계를 따로 돌려 그때 화면을 다시 그렸습니다. egui 는 프레임마다
도는 방식이라 시계가 필요 없습니다. 다음 프레임을 그 시각에 맞춰 달라고
해 두고(`request_repaint_after`), 그 프레임에서 지났는지 보면 됩니다.
실이 하나도 늘지 않습니다.

## 데스크톱 화면 (crates/ui)

### 엔진이 원본, 화면은 거울

Go 판(Fyne)은 위젯이 스스로 상태를 들고 있어서 엔진을 건드릴 때마다
`refresh()` 로 맞춰 주어야 했습니다. egui 는 매 프레임 화면을 처음부터
다시 그리므로 그 함수가 아예 없습니다. **엔진을 읽어서 그리면 그것이 곧
갱신입니다.** 화면이 상태를 들고 있지 않으니 어긋날 자리도 없습니다.

### 편집 영역

egui 의 여러 줄 입력칸을 쓰되 **직접 타이핑하지 못하게** 막습니다.
프레임 맨 앞에서 키 · 글자 · 붙여넣기 · 복사 이벤트를 우리가 먼저 처리하고,
처리한 뒤 egui 의 이벤트 줄에서 걷어냅니다. 그래서 입력칸에 닿는 것은
마우스뿐입니다. C++ 판이 읽기 전용 `EDIT` 컨트롤을 서브클래스해서 하던
일과 같습니다.

입력칸에 넘기는 글은 엔진에서 뜬 **사본**입니다. 사본이 고쳐지더라도
엔진으로 되돌리지 않으므로 다음 프레임에 엔진 내용으로 덮입니다.

엔진은 커서를 "몇 번째 글자" 하나로 들고, 입력칸은 (줄, 칸) 두 값으로
듭니다. `row_col_of()` / `flat_pos_of()` 가 그 사이를 옮깁니다.
찍은 자리는 엔진 커서로 되돌리고, 그 밖에는 늘 엔진 값으로 맞춥니다.

### 커서를 늘 보이게 · 굼떠 보이지 않게

깜박이는 막대가 한 박자 늦게 따라오면 화면이 깜빡이는 것처럼 보이고
반응이 느리게 느껴집니다. 그러지 않도록 두 가지를 지킵니다.

**커서 자리를 그리기 전에 심습니다.** 그린 뒤에 심으면 그 판에는 옛 자리가
그려지고 새 자리는 다음 판에나 나옵니다. egui 는 입력이 있을 때만 다시
그리므로, 그 다음 판은 다음 입력이 올 때까지 오지 않습니다. 글자는 바로
찍히는데 막대만 뒤늦게 따라오는 것이 그래서였습니다.

**초점을 놓지 않게 합니다.** egui 의 기본값은 "초점 밖을 누르면 놓는다"
입니다. 키패드를 누를 때마다 편집칸이 초점을 놓았다가 다음 판에 되찾았고,
그 사이 막대가 사라져 깜빡였습니다. 물리 키보드는 어차피 우리가 먼저
가로채므로 초점을 넘길 까닭이 없습니다. 그래서
`SurrenderFocusOn::Never` 로 못박습니다.

### 버튼

키패드 버튼과 툴바 버튼은 egui 의 기본 단추를 쓰지 않고 직접 그립니다.
역할(자음 / 모음 / 문장부호 / 기능 / 모드 / 툴바)마다 색이 달라야 하는데,
겉모습을 정하는 `Visuals` 는 위젯 하나하나에 다른 색을 주지 못하기 때문입니다.
C++ 판이 `BS_OWNERDRAW` 로 하던 일과 같습니다.

자리는 `layout.rs` 가 미리 셈해서 알려 줍니다. 그 셈은 화면을 하나도
건드리지 않는 순수한 계산이라 창 없이 시험할 수 있습니다.

### 창 폭과 툴바

창의 최소 폭은 **툴바가 정합니다.** 툴바 열한 칸이 다 보이는 가장 좁은
폭을 셈해서(`TOOLBAR_MIN_W`) 그것을 창의 최소 폭이자 처음 폭으로 씁니다.
버튼 수나 크기를 고치면 창 폭이 저절로 따라갑니다. 그보다 넓혀 봐야
편집칸 양옆만 비므로 처음 폭도 같게 두었습니다.

창 관리자가 최소 크기를 지키지 않거나 프로그램이 창 크기를 직접 바꾸는
일이 있습니다. 그때는 **버튼을 줄여서라도 열한 칸을 모두 보입니다.**
몇 개를 잘라 내는 것보다 작게라도 다 보이는 편이 낫습니다.
`toolbar_never_clips` 가 아주 좁은 폭까지 훑어 겹치거나 판 밖으로 나가는
칸이 없는지 봅니다.

### 그림

Fyne 은 아이콘을 들고 있었고 웹 판은 인라인 SVG 를 씁니다. egui 에는
아이콘 꾸러미가 없으므로 같은 모양을 선으로 직접 그립니다(`icons.rs`).
좌표는 웹 판과 같은 24x24 자리에 적어 두어 두 판의 그림이 같습니다.

이모지를 쓰면 시스템마다 색과 크기가 달라지고, 글꼴 문자 `↵`(U+21B5) 와
`⌫`(U+232B) 는 내장한 Noto Sans KR 에 없어서 빈칸이 됩니다. 그래서 그
두 자리는 반드시 그림이어야 합니다. `button_tables_match` 시험이 기능
버튼마다 글자든 그림이든 하나는 있는지 봅니다.

### 글꼴

egui 의 기본 글꼴에는 한글이 없어서 **Noto Sans KR 을 실행 파일에 넣습니다.**
완성형 11172자를 모두 담고 있어야 `갂 갃` 같은 글자도 그려집니다.

가변 글꼴 `NotoSansKR[wght].ttf` 를 그대로 넣으면 안 됩니다.
그 글꼴은 `wght` 축의 **기본값이 100(Thin)** 이라서 글자가 아주 가늘게,
흐릿하게 나옵니다. 그래서 400 과 700 으로 미리 뽑아 둔 두 벌을 넣습니다.

```sh
python -m fontTools.varLib.instancer -o NotoSansKR-Regular.ttf NotoSansKR[wght].ttf wght=400
python -m fontTools.varLib.instancer -o NotoSansKR-Bold.ttf    NotoSansKR[wght].ttf wght=700
```

굵은 벌은 `FontFamily::Name("chunjiin-bold")` 라는 갈래로 등록하고,
버튼과 상태줄이 그 갈래를 못박아 씁니다.

**글꼴 등록은 첫 판을 그리기 전에 끝나야 합니다.** `set_fonts` 는 다음
판부터 듣기 때문에, 그리는 도중에 부르면 굵은 갈래를 찾다가 죽습니다.
그래서 앱을 만드는 길을 `App::new_in(ctx)` 하나로 좁히고 거기서 등록합니다.
시험이 이것을 실제로 잡아냈습니다.

### 테마

색은 모두 `PALETTES` 표에서 가져옵니다. C++ 판 `THEMES[]` · Go 판
`Palettes` 와 같은 값입니다. 창 배경 · 카드 · 테두리 · 글자 · 흐린 글자와,
버튼 역할마다 다섯 가지 색(기본 · 호버 · 눌림 · 테두리 · 글자)을 갖습니다.

`visuals_for()` 는 팔레트만으로 egui 가 그리는 모든 색을 냅니다.
정하지 않고 egui 기본값에 맡기는 자리를 두지 않습니다. 그렇게 두면
어떤 테마에서 글자가 배경에 묻힙니다.

egui 는 밝은 겉모습과 어두운 겉모습을 따로 듭니다. 우리는 테마가 색을
정하므로 **양쪽에 같은 값을 넣습니다**(`all_styles_mut`). 그러지 않으면
운영체제의 밝기 설정이 우리 팔레트를 뒤엎습니다.

### 언어

`Strings` 구조체 하나에 화면에 나오는 모든 글자가 들어 있습니다.
구조체이므로 **항목을 하나 빠뜨리면 컴파일이 되지 않습니다.**
`lang_tables_complete` 가 두 언어의 모든 칸이 비지 않았는지 전수로 봅니다.

### 딸린 창

사용법 · 정보 · 설정은 진짜 창으로 띄웁니다(C++ 판도 그랬습니다).
egui 의 "곧바로 그리는 창"(`show_viewport_immediate`)을 씁니다. 이 방식은
본문이 `App` 을 그대로 빌려 쓸 수 있어서, 창마다 상태를 따로 나눠 들
필요가 없습니다.

#### 창을 내용에 딱 맞추기

세 창 모두 스크롤 막대가 없고, 단추 아래에 빈 자리가 남지 않습니다.
크기를 못박지 않고 내용에 맞추기 때문입니다.

- **폭**은 그리기 전에 글자를 재어 정합니다(`help_width`, `settings_width`,
  `about_width`). 말을 바꾸면 글자 길이가 달라지므로 손으로 적어 두지
  않습니다.
- **높이**는 그 폭으로 한 판 그려 보고 잽니다.

여기에는 함정이 둘 있었습니다.

**하나.** `CentralPanel` 은 스스로를 창 전체로 부풀립니다
(`expand_to_include_rect`). 그래서 그 판의 자리를 재면 내용이 아무리
작아도 늘 창 크기가 나옵니다. 본문을 따로 만든 상자(`scope_builder`)에
담고, 그 상자가 스스로 차지한 자리를 알려 주게 해야 합니다.

**둘.** 남은 자리를 다 차지하는 위젯이 하나라도 끼면 잰 값이 무의미해집니다.
`ui.separator()` 가 가로로 놓인 칸 안에서는 세로줄이 되어 남은 높이를 다
먹었고, 오른쪽 정렬 단추 줄도 마찬가지였습니다. 그래서 사이 줄은 길이를
못박아 직접 긋고, 단추 줄은 높이를 정해 자리를 잡습니다.
`help_body_measures_its_own_size` 가 이 두 가지가 되살아나지 않는지 봅니다.

#### 사용법 창을 두 칸으로

사용법은 70줄입니다. 한 줄로 세우면 창이 화면보다 길어져 스크롤이
생깁니다. 그래서 `[ 제목 ]` 단위로 잘라 두 칸에 나눠 놓습니다
(`help::two_columns`). 구역 하나를 두 칸에 걸쳐 놓지는 않습니다.
읽는 차례가 끊기기 때문입니다.

### 설정

`Settings` 를 JSON 파일 하나로 저장합니다. **칸 이름과 값은 Go 판과
같습니다.**

```
Windows  %AppData%\Chunjiin\settings.json
macOS    ~/Library/Application Support/Chunjiin/settings.json
Linux    ~/.config/Chunjiin/settings.json
```

경로를 만드는 함수는 갈아 끼울 수 있게 두었습니다. 시험이 그것을 임시
폴더로 돌려세우기 위해서입니다. 환경 변수를 건드리는 것만으로는 운영체제
마다 다른 설정 폴더를 확실히 돌려세울 수 없어, 실제 사용자 설정을 덮어쓸
위험이 있었습니다.

## 웹 화면 (web/)

조합은 하나도 자바스크립트에서 하지 않습니다.
키를 누르면 `chunjiin_wasm` 으로 넘기고, 돌아온 상태 객체로 화면을 다시
그립니다.

```
누름 → engine.key(i) → 상태(JSON) → render(상태)
```

`crates/wasm` 이 엔진 함수들을 `wasm-bindgen` 으로 내보냅니다.
**모든 함수가 처리를 마친 뒤의 상태를 JSON 으로 돌려주므로**, 부른 쪽은
따로 상태를 다시 물을 필요가 없습니다. 상태는 열몇 칸짜리라 글로 만들었다
푸는 값이 싸고, 자바스크립트 쪽에서는 `JSON.parse` 하나로 끝납니다.

Go 판은 `wasm_exec.js` 와 전역 객체를 썼습니다. wasm-bindgen 은 모듈을
만들어 주므로 `app.js` 가 모듈이 되었습니다(`<script type="module">`).

- 편집칸은 진짜 `<textarea>` 입니다. 그래야 브라우저가 커서 · 선택 · 스크롤을
  맡아 줍니다. `beforeinput` 을 막아 직접 편집은 못 하게 합니다.
- 글꼴은 내려받지 않고 시스템 한글 글꼴을 씁니다. 더 또렷하고, 6MB 짜리
  글꼴을 받게 하지 않아도 됩니다.
- 색은 CSS 변수로 두고 `<body data-theme="...">` 를 갈아 테마를 바꿉니다.
  값은 데스크톱 판 `PALETTES` 와 같습니다.
- 설정은 `localStorage` 에 넣습니다.
- 툴바 아이콘은 인라인 SVG 입니다. 이모지를 쓰면 시스템마다 색과 크기가
  달라집니다.

WASM 은 약 **44 KB** 입니다. Go 판은 같은 자리에 1.8 MB 였습니다.
Rust 는 실행 시간에 딸려 오는 것(가비지 컬렉터 등)이 없어서입니다.

## 실행 파일에 무엇을 품는가

Go 의 `go:embed` 에 해당하는 것이 Rust 에는 없습니다. 그래서 빌드할 때
`build.rs` 가 폴더를 훑어 `include_bytes!` 목록을 만들어 둡니다.
꾸러미를 더 들이지 않고 같은 일을 합니다.

| 무엇 | 어디에 | 누가 만드나 |
|---|---|---|
| 글꼴 · 아이콘 | `crates/ui` | `include_bytes!` 한 줄 |
| 웹 판 전체 | `crates/serve` | `crates/serve/build.rs` |
| 앱 실행 파일 | `crates/setup` | `crates/setup/build.rs` |
| 빌드에 쓴 rustc 판 | `crates/ui` | `crates/ui/build.rs` |

## 설치 프로그램

`crates/setup` 은 C++ 판 `installer/setup.c` 와 같은 생각입니다.
실행 파일을 자기 안에 품고 있다가 설치 폴더에 풉니다.
관리자 권한이 필요 없고, 다른 설치 도구를 깔지 않아도 됩니다.

- **Windows** — 실행 파일을 놓고, PowerShell 의 `WScript.Shell` 로 시작 메뉴
  바로 가기를 만들고, `reg.exe` 로 `HKCU\...\Uninstall\Chunjiin` 에 등록
  정보를 씁니다. 레지스트리 꾸러미를 들이지 않는 까닭은 쓰는 값이 여섯
  개뿐이고 `reg.exe` 가 Windows 에 늘 있기 때문입니다.
  제거할 때는 자기 자신이 그 폴더에서 돌고 있으면 지울 수 없으므로,
  잠깐 기다렸다 지우는 `cmd` 를 띄우고 물러납니다.
- **Linux** — `~/.local/share/Chunjiin` 에 놓고, `~/.local/bin` 에 링크를 걸고,
  `.desktop` 항목과 아이콘을 만듭니다.
- **macOS** — `~/Applications/Chunjiin.app` 묶음을 만듭니다.

품고 있는 실행 파일은 `scripts/package.*` 가 빌드해서 `payload/` 에 넣고,
설치 프로그램을 빌드한 뒤 지웁니다. 저장소에 남지 않습니다.

## 시험

### 기대값을 손으로 옮겨 적지 않는다

조합 규칙의 기대값은 C++ 판 `tests/test_engine.c` 에 이미 있습니다.
그걸 Rust 로 옮겨 적으면, 원본이 고쳐졌을 때 조용히 어긋납니다.
그래서 **그 파일에서 직접 뽑아 옵니다.**

```
KoreanChunJiInC++/tests/test_engine.c
        │
        │  cargo run -p gen-testcases
        ▼
test/cases.tsv                          27구역 430항목
        │
        │  crates/engine/tests/cases.rs 가 읽어 돈다
        ▼
   cargo test
```

뽑아낸 결과는 저장소에 함께 둡니다. C++ 판이 없는 곳에서도 시험은 그대로
돌아갑니다. Go 판이 뽑아낸 것과 한 줄도 다르지 않습니다.

뽑아 오는 것은 `expect` 계열 호출과 표로 적힌 줄입니다.
C 코드에서도 계산으로 만들어지는 것(영문 26자 전수, 라벨-입력 일치)과
원본 함수를 직접 부르는 것(`get_unicode`, `check_double`)은 뽑을 수 없어
`crates/engine/tests/engine.rs` 에 Rust 로 적어 둡니다.

시험은 꾸러미마다 그 곁에 둡니다. Rust 의 통합 시험은 공개 API 만 보므로,
공개하지 않은 것을 보아야 하는 시험은 그 꾸러미 안에 둡니다.

| 자리 | 무엇 |
|---|---|
| `crates/engine/tests/` | 엔진 회귀 시험(자료 · 계산) |
| `crates/ui/tests/` | 색표 · 설정 · 배치 · 커서 · 언어 · 그림 · 스모크 |
| `crates/serve/src` | 경로 다듬기 · MIME · 주소 표시 |
| `crates/testkit/src` | 자료 읽기와 따옴표 풀기 |
| `crates/testreport/src` | 보고기 자체 |

### 비교 축

| 종류 | 확인하는 것 |
|---|---|
| `expect` | 확정 후 텍스트 버퍼 |
| `live` | 확정하지 않은, 조합 중인 화면 |
| `cursor` | 버퍼 + 커서 위치 |
| `comp` | 상태줄 조합 표시 |
| `mode` | 모드 이름 |

### 시험이 스스로를 지키는 장치

- `cases_file_shape` — 뽑아 온 항목이 430개인지 본다. 뽑개가 조용히 망가지면
  시험이 통째로 비어도 통과해 버리기 때문이다.
- `key_labels` — 다섯 모드 × 12키. 버튼에 적힌 글자와 실제로 들어가는
  글자가 같은지 본다.
- `button_tables_match` — 기능 버튼이 글자든 그림이든 하나는 갖는지 본다.
- `lang_tables_complete` — 두 언어 글자표에 빈 칸이 없는지 본다.
- `palettes` · `theme_visuals` — 테마가 비치는 색이나 안 보이는 색을 두지
  않는지 본다.
- `weighted_row_layout` — 기능 버튼 줄이 오른쪽 끝에 정확히 닿는지 본다.
- `cursor_round_trip` — 커서 표현 두 가지를 오갔을 때 제자리로 오는지 본다.
- `app_smoke` — 창을 실제로 만들어 테마 4종 · 모드 5종 · 딸린 창 셋 ·
  언어 2종을 모두 그려 본다. 그리고 키를 눌러 편집칸에 그 글자가
  들어가는지까지 본다. egui 는 그리는 데 창이 필요 없으므로 화면 없는
  곳에서도 그대로 돈다.
- `toolbar_never_clips` — 아주 좁은 폭까지 훑어 툴바 열한 칸이 겹치거나
  판 밖으로 나가지 않는지 본다.
- `help_body_measures_its_own_size` — 사용법 창 본문이 스스로 정한 자리
  안에만 머무는지 본다. 남은 자리를 다 차지하는 위젯이 끼면 창을 내용에
  맞출 수 없어 빈 자리가 크게 남는다(실제로 겪은 일이다).
- `empty_report_is_visible` — 보고기가 "0개 중 0개 통과" 로 조용히 넘어가지
  않는지 본다.

전부 합쳐 **754항목**입니다.

### 결과를 어떻게 보여 주는가

`cargo test` 는 시험 함수마다 ok/FAIL 만 찍어서, 그 안에서 무엇을 얼마나
보고 있는지 알 수 없습니다. C++ 판 `test_engine` 은 구역별 집계와 전체
요약을 보여 주었는데 그 편이 훨씬 낫습니다.

그래서 시험이 항목마다 한 줄을 남기고(`chunjiin-testkit`), `chunjiin-testreport`
가 `cargo test` 를 돌려 그 줄을 모아 정리합니다.

```
@@CASE<탭>ok<탭>묶음<탭>구역<탭>이름<탭>설명
```

- 묶음(`조합 엔진 · C++ 원본에서 뽑아 온 자료` 등)과 구역으로 나눕니다.
- `-v` 를 주면 항목마다 무엇을 눌러 무엇이 나와야 하는지 한 줄씩 보여 줍니다.
  이름만으로는 그 항목이 무엇을 보는지 알 수 없기 때문입니다.
- 실패하면 어느 구역의 어느 항목이 왜 틀렸는지 따로 모아 보여 줍니다.
- 항목을 하나도 모으지 못하면 그것을 잘못으로 알립니다. 그러지 않으면
  시험이 빌드되지 않았을 때 "모두 통과" 로 보입니다.

보고기 자체도 시험합니다. 보고기가 조용히 망가지면 헛된 요약을 보고
다 잘 돌아간다고 믿게 되기 때문입니다.
