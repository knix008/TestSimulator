MyCodeChecker 사용 설명서

MyCodeChecker는 내 컴퓨터에서 돌아가는 코드 품질 · 보안 작업대입니다. 소스 폴더를 열고 분석하면 버그 · 취약점 · 코드 스멜 · 보안 핫스팟, 중복, 커버리지, 등급과 품질 게이트를 보여 주고(코드 품질), C/C++ 결함을 경로와 함께 추적하며(정밀 결함 분석), 행정안전부 보안약점 · MISRA · CERT 같은 기준의 준수 여부와 예외 승인을 관리합니다(보안 약점 점검).

분석은 프로그램 안의 Node.js 엔진이 합니다. 데스크톱 프로그램(Windows · macOS · Linux)과 웹판은 같은 엔진과 같은 화면을 씁니다. 분석하는 동안 소스 코드는 컴퓨터 밖으로 나가지 않습니다. 밖으로 보내는 기능은 사용자가 직접 켜는 AI 코드 수정과 온라인 확인 (OSV.dev) 둘뿐입니다.

설치 #

데스크톱 (Windows · macOS · Linux) #

OS설치 파일메모
WindowsMyCodeChecker_<버전>_x64-setup.exe (NSIS)WebView2 가 없으면 설치 프로그램이 받아 옵니다
macOS.dmg (안에 .app)처음 열 때 "확인되지 않은 개발자" 경고가 나오면 Finder 에서 오른쪽 클릭 › 열기
Linux.deb 또는 .AppImageAppImage 는 실행 권한(chmod +x)을 주고 실행합니다

설치본에는 Node.js 와 분석 엔진이 들어 있습니다. 다른 프로그램을 설치하지 않아도 분석할 수 있습니다.

Windows 설치 언어 — 설치 프로그램은 처음에 한국어 / English 중 설치 언어를 묻습니다(다시 설치할 때도 묻고, 지난번 선택이 기본으로 골라져 있습니다). 고른 언어로 설치 화면이 나오고, 설치한 뒤 처음 실행할 때 프로그램 언어도 그 언어로 맞춰집니다. 그 뒤에 프로그램에서 바꾼 언어는 다음 설치 전까지 그대로 유지됩니다.

Windows 설치 끝의 Git 질문 — 설치가 끝날 때 Git 이 없으면 "Git이 설치되어 있지 않습니다 … 지금 winget으로 Git을 설치할까요?" 를 묻습니다. 예를 누르면 winget 으로 Git 을 설치하고, 아니요를 누르면 그냥 끝납니다. winget 이 없는 컴퓨터에서는 내려받기 주소만 알려 줍니다. 조용한 설치(/S)는 아무것도 더 설치하지 않습니다. 나중에 도구 › 필요한 소프트웨어… 에서 언제든 설치할 수 있습니다.

처음 시작할 때 — 필요한 소프트웨어 #

프로그램이 처음 작업 공간을 읽으면, 일부 기능이 쓰는 외부 프로그램을 찾아보고 없는 것이 있으면 필요한 소프트웨어 설치 창을 띄웁니다. "설치"를 누르기 전에는 아무것도 설치하지 않습니다.

프로그램구분쓰는 곳없으면
Git권장새 코드(SCM 기준), 작성자 자동 할당, 풀 리퀘스트 분석, 데스크톱 분석새 코드는 이전 분석과 비교해 정하고, 작성자 할당과 PR 분석은 꺼집니다
C/C++ 컴파일러 (LLVM / Clang)선택C/C++ 빌드 캡처(npm run defects -- build)빌드 없이(buildless) 분석할 수 있습니다

도구마다 설치 · 나중에(다음 시작 때 다시 물음) · 다시 묻지 않음 을 고릅니다. 실행할 명령과 명령 복사로 패키지 관리자 명령(winget · scoop · Homebrew · apt · dnf · pacman · zypper)을 직접 실행해도 됩니다. 쓸 수 있는 패키지 관리자가 없으면 내려받기 페이지를 엽니다. 같은 내용은 관리 › 필요한 소프트웨어 탭에도 있고, 시작할 때 확인을 끄면 시작할 때 묻지 않습니다.

웹판 #

브라우저에서 쓰려면 개발 폴더에서 npm run web 을 실행하고 http://127.0.0.1:5211 을 엽니다. 팀 서버로 쓸 때는 node server/server.js --host 0.0.0.0 --port 5211 처럼 띄우고, 관리 › 사용자 · 권한에서 권한 검사를 켭니다. 웹판에서는 폴더 선택 창 대신 서버에서 본 폴더 경로를 적습니다.

탭 #

가운데 영역은 탭으로 열립니다. 홈(시작 화면)은 맨 앞에 고정되고, 탐색이나 메뉴로 연 보기는 아이콘 + 이름의 탭이 됩니다.

  • 탭의 × 나 가운데 단추 클릭으로 닫고, 끌어서 순서를 바꿉니다.
  • 탭에서 오른쪽 클릭: 탭 닫기 · 다른 탭 닫기 · 오른쪽 탭 닫기 · 모두 닫기.
  • 탭이 넘치면 < >(누르면 한 칸, 누르고 있으면 계속)와 ⌄(열린 탭 모두 보기)가 나옵니다.
  • Ctrl+Tab / Ctrl+Shift+Tab 은 다음 · 이전 탭, Ctrl+W 는 지금 탭을 닫습니다.

목록 보기(이슈 · 규칙 · 의존성 · 웹 스캔 결과 · 예약 분석 등)는 제목 · 필터 · 열 머리글이 제자리에 있고 행만 스크롤됩니다. 창이 아주 작아 머리글만으로 자리가 차면 보기 전체가 스크롤됩니다.

패널 #

  • 왼쪽 패널 — 탐색. 다섯 무리(프로젝트 · 이슈 · 정밀 결함 분석 · 보안·규정 · 관리)로 보기를 나눕니다. 무리 이름을 누르면 접고 펼치며, 위의 모두 펼치기 · 모두 접기로 한꺼번에 바꿉니다. 이슈 · 보안 핫스팟 · 결함 · 예외 승인 옆의 숫자는 열린 이슈, 검토할 핫스팟, 남은 결함, 승인을 기다리는 예외 신청 수입니다.
  • 오른쪽 패널 — 세부 정보. 목록에서 고른 항목의 세부 정보가 여기에만 나옵니다: 이슈(코드 · 이유 · 고치는 법 · 처리 단추 · 티켓 · AI 코드 수정), 결함(이벤트 경로 · 분류), 보안 핫스팟, 규칙, 파일, 아키텍처 모듈. 고른 항목이 없으면 "선택한 항목이 없습니다." 가 나옵니다.
  • 아래 패널 — 탭 네 개입니다.
    • 문제 — 지금 보기에 맞는 이슈(코드 보기에서는 그 파일의 열린 이슈, 핫스팟 보기에서는 검토할 보안 핫스팟, 결함 보기에서는 남은 결함, 그 밖에는 열린 이슈). 줄을 누르면 그 위치로 갑니다.
    • 분석 로그 — 마지막 작업의 상태 · 브랜치 · 시각, 걸린 시간, 파일 수 · 코드 줄 · 언어, 엔진별 결과 수, 커버리지, 품질 게이트, 엔진 경고.
    • 작업 — 진행 중인 분석 · 웹 스캔 · 소프트웨어 설치, 예약 분석의 마지막 실행과 다음 실행.
    • 출력 — 프로그램이 남긴 메시지(시각과 함께). 지우기 단추가 있습니다.

패널마다 머리글의 접기 단추를 누르면 아이콘과 제목만 있는 띠로 접히고, 띠를 누르면 펼치기 됩니다. 패널 닫기나 도구 모음의 토글로 아예 끕니다. 패널 사이 분할선을 끌면(또는 분할선에 초점을 두고 화살표 키) 폭과 높이가 바뀝니다. 켜짐 · 접힘 · 크기는 저장되며, 설정 › 고급 › 패널 크기·배치 초기화로 처음 배치로 돌아갑니다.

상태 표시줄 #

열린 프로젝트 이름과 경로, 마지막 메시지(예: "품질 게이트를 통과했습니다."), 파일 수, 코드 줄, 품질 게이트 통과/실패가 나옵니다. 오른쪽 아래 크기 조절 표시를 끌어 창 크기를 바꿉니다.

용어 · 버튼 툴팁 #

점선 밑줄이 있는 용어(등급, 기술 부채, 중복 줄 %, 커버리지, 코드 줄, Ca · Ce · I, HIS 지표, CID, 영향, 체커, 심각도 …)에 마우스를 올리거나 키보드로 초점을 옮기면 그 용어의 이름과 뜻이 툴팁으로 나옵니다(Esc로 닫음). 버튼 · 메뉴 · 탭 · 탐색 항목 · 설정 레이블에 마우스를 올려도 그 기능이 무엇을 하는지 설명이 나옵니다(풀 리퀘스트 분석 화면 포함). 아키텍처 · HIS 메트릭 · 결함 · 풀 리퀘스트 화면 위에는 그 화면의 용어를 모은 용어 설명도 있습니다.

실행 취소와 다시 실행 #

편집 › 실행 취소(Ctrl+Z)는 마지막 변경을 되돌리고, 다시 실행(Ctrl+Y 또는 Ctrl+Shift+Z)은 되돌린 것을 다시 합니다. 도구 모음의 같은 단추에 마우스를 올리면 "실행 취소: 품질 게이트 변경" 처럼 작업 이름이 보이고, 실행하면 "실행 취소함: …" 이 잠깐 나옵니다. 되돌릴 수 있는 것:

  • 이슈의 상태 · 해결 · 담당 · 태그 변경(이슈 하나든, 선택 항목에 적용으로 여러 개든 한 번에)
  • 품질 게이트 · 품질 프로파일 · 포트폴리오 · 정밀 결함 분석 정책 · 사용자 규칙 편집
  • 프로젝트 설정(관리 › 분석 설정의 값, 프로젝트 이름 등)
  • 패널 켜기/끄기 · 접기, 시작 화면 카드 배치(옮기기 · 크기 · 자동 정렬)
  • AI 코드 수정 적용 — 실행 취소하면 파일을 수정 전으로 되돌립니다. 적용한 뒤 파일이 또 바뀌었으면 되돌리지 않고 알려 줍니다

새 작업을 하면 다시 실행 목록은 비워지고, 다른 프로젝트를 열면 둘 다 비워집니다(최근 100개까지 기억).

분석 진행 창 #

분석이 1초쯤 넘게 걸리면 분석 진행 중 창이 나옵니다.

  • 단계 — 파일 수집 중 → 규칙 실행 중 → 엔진 실행 중: {엔진} → 마무리 중
  • 지금 읽는 파일이나 돌고 있는 엔진, 진행률(%) 막대, 지난 시간 · 남은 시간
  • 취소 — "진행 중인 분석을 멈출까요?" 를 확인한 뒤 멈춥니다. 취소한 분석은 결과를 저장하지 않으며, 백그라운드 작업에는 실패(FAILED)가 아닌 취소됨(CANCELED)으로 남습니다.

같은 프로젝트를 분석하는 중에 다시 분석을 시작하면 새로 돌리지 않고 진행 중인 분석에 연결합니다("이 프로젝트는 이미 분석 중입니다…"). 분석하는 동안 이슈 처리(상태 · 담당 · 의견)나 설정을 바꿔도 되며, 분석이 끝나 결과를 저장할 때 그 변경이 그대로 남습니다.

진행 팝업 #

큰 프로젝트의 이슈를 불러오거나 보고서 · 아키텍처 · HIS 메트릭 · 의존성처럼 내용이 많아 0.6초 넘게 걸리는 작업은 오른쪽 아래 팝업에 작업 이름, 진행 막대(전체 양을 알면 개수와 %), 지난 시간을 보여 줍니다. 여러 작업이 겹치면 3개까지 보이고 나머지는 "외 n건"으로 줄입니다.

오류 메시지 #

오류는 화면 언어(한국어 / English)로 나오고, 필요하면 코드가 함께 붙습니다.

프로젝트 파일과 샘플 #

프로젝트 파일 (.mccp) #

폴더를 그냥 열어도 분석할 수 있지만, 프로젝트 파일(*.mccp)을 만들면 소스 폴더와 프로젝트 설정을 파일 하나에 담아 팀과 함께 쓸 수 있습니다(코드 옆에 커밋). 데스크톱에서는 .mccp 파일을 두 번 누르면 MyCodeChecker 가 그 프로젝트를 엽니다(전용 파일 아이콘).

  • 파일 › 새 프로젝트…(Ctrl+N) — 이름(예: 결제 서버) · 소스 폴더(찾아보기…) · 프로젝트 파일(기본 <소스 폴더>\<키>.mccp), 더 많은 설정: 기본 브랜치 · 설명 · 제외 패턴. 포함 디렉터리 · 매크로 · 커버리지 같은 나머지 설정은 관리 › 분석 설정에서 바꾸고 프로젝트 저장으로 파일에 씁니다. 만든 뒤 바로 분석을 켜고 만들기. 같은 이름의 파일이 있으면 덮어쓰기를 묻습니다. 소스 폴더가 이미 프로젝트로 등록되어 있으면 "이 폴더는 이미 '…' 프로젝트로 등록되어 있습니다. 바꾸시겠습니까?" 와 함께 바꾸기(새 설정으로 바꿈) · 기존 프로젝트 열기 · 취소를 고릅니다.
  • 파일 › 프로젝트 열기…(Ctrl+Shift+O) — .mccp 경로를 적거나 최근 프로젝트 파일에서 고릅니다.
  • 파일 › 프로젝트 저장(Ctrl+S) · 다른 이름으로 저장…(Ctrl+Shift+S) — 지금 프로젝트 설정을 파일에 씁니다. 이 프로젝트를 연 파일이 아닌, 이미 있는 .mccp 에 쓰려 하면 먼저 묻습니다: 바꾸기 · 다른 위치에 저장… · 취소.
  • 파일 › 프로젝트 삭제(또는 관리 화면의 프로젝트 삭제) — 확인한 뒤 프로젝트와 그 분석 기록을 작업 공간에서 지웁니다. 소스 폴더와 .mccp 파일은 지우지 않으므로 나중에 다시 열 수 있습니다.
  • 파일 › 최근 프로젝트 — 1–10 번, 목록 지우기.

저장하지 않은 변경 — 프로젝트 설정이나 열린 편집기(설정 창, 규칙 · 게이트 · 프로파일 편집, 새 프로젝트 창)에 저장하지 않은 변경이 있으면 제목에 ● 가 붙습니다(마우스를 올리면 "저장하지 않은 변경사항이 있습니다"). 창을 닫거나 끝내기를 하면 무엇이 바뀌었는지 보여 주고 저장 · 저장 안 함 · 취소를 묻습니다.

이전 버전에서 만든 파일 — 이전 버전이 만든 작업 공간(workspace.json)과 프로젝트 파일은 처음 열 때 자동으로 지금 형식으로 바뀝니다. 이슈 · 결함의 처리 상태(상태 · 분류 · 담당 · 의견)는 그대로 이어집니다.

파일은 JSON 입니다: name, key, source(프로젝트 파일 기준 상대 경로라서 폴더를 옮겨도 그대로 동작), settings(mainBranch, exclusions, includeDirs, defines, coverageReports, arch, newCode, profiles, gateId, policyId, description …). 분석 결과와 이슈 상태는 파일이 아니라 작업 공간에 저장됩니다.

{
  "format": "mycodechecker-project",
  "version": 1,
  "name": "C++ 센서 로거",
  "key": "cpp-sensor",
  "source": ".",
  "settings": { "mainBranch": "main", "includeDirs": ["include"], "defines": { "SENSOR_VERSION": "2" } }
}

첫 분석 #

  1. 폴더 열기…(Ctrl+O, 도구 모음 열기)로 분석할 소스 폴더를 고릅니다. 설정을 파일로 남기려면 새 프로젝트…(Ctrl+N)로 프로젝트 파일을 만듭니다. 데스크톱은 폴더 선택 창, 웹판은 폴더 경로 입력 창(전체 경로를 적고 Enter)이 나옵니다. 연습은 샘플 프로젝트로 합니다.
  2. 바로 분석이 시작되고 분석 진행 창과 아래 패널 작업에 진행이, 분석 로그에 결과가 나옵니다. 끝나면 개요가 열리고 상태 표시줄에 게이트 결과가 나옵니다.
  3. 코드를 고친 뒤 다시 분석하려면 도구 모음의 분석(Ctrl+Enter)을 누릅니다. 스트림을 바꾸지 않고 새 결함만 보려면 데스크톱을 누릅니다. 두 번째 분석부터는 이전 분석과 비교한 새 코드 결과가 따로 나옵니다.

분석에서 빠지는 것: node_modules, .git, dist, build, target, vendor, bin, obj, coverage, .mcc 같은 폴더, 설정의 제외 패턴에 맞는 파일, 프로젝트의 분석 제외 폴더, 800 KB 보다 큰 파일, 바이너리 파일.

프로젝트 설정: 왼쪽 탐색의 프로젝트 › 프로젝트 설정(또는 파일 › 프로젝트 설정…)에서 이 프로젝트를 다시 분석할 때 쓰는 설정을 한곳에서 바꿉니다. 기본 정보(이름 · 키 · 설명 · 태그 · 주 브랜치, 소스 폴더는 보기만), 프로젝트 언어(코드에서 찾은 언어가 자동으로 들어가고, 언어 추가로 더할 수 있음 — 언어별 품질 프로필과 엔진의 기본 선택이 이 언어를 따름), 분석 엔진(MISRA C:2012/2023 · MISRA C:2004 · MISRA C++:2023 · MISRA C++:2008 · AUTOSAR C++14 · CERT 등 검사 항목을 하나씩 켜고 끔. 이 프로젝트만 따로 정하기를 켜지 않으면 설정 › 분석의 선택을 따르고, 켜면 프로젝트 언어에 맞는 엔진이 기본으로 선택되고 필요한 엔진을 더 켤 수 있음 — 언어에 맞게 선택으로 다시 맞춤), 규칙 · 게이트(품질 게이트 · 결함 정책 · 언어별 품질 프로필, "기본"은 작업 공간 기본값, 적용 안 함을 고른 언어는 분석하지 않음), 분석 범위(제외 패턴 · 분석 제외 폴더), C/C++ 포함 폴더와 매크로, 이 프로젝트만의 새 코드 기준, 커버리지 보고서 경로입니다. 저장하면 다음 분석부터, 저장 후 다시 분석은 바로 적용됩니다. 저장은 실행 취소(Ctrl+Z)할 수 있습니다. 제외 패턴의 **/ 는 폴더가 없는 경우도 뜻하므로 **/dup/** 는 맨 위의 dup/ 폴더도 뺍니다.

분석 제외 폴더: 파일 › 분석 제외 폴더…(또는 관리 › 분석 설정의 분석 제외 폴더, 새 프로젝트 대화상자의 더 보기)에서 소스 폴더의 트리를 펼쳐 빼고 싶은 폴더에 체크합니다. 체크한 폴더와 그 아래 모든 파일은 분석하지 않습니다. 이름이 같은 다른 위치의 폴더(예: apis 를 빼도 src/apis 는 분석)는 그대로 둡니다. 항상 건너뛰는 폴더에는 항상 제외 가 붙습니다. 다음 분석부터 적용되고, 프로젝트 파일(.mccp)의 excludeDirs 에 저장됩니다.

결과 삭제 후 다시 분석: 파일 › 결과 삭제 후 다시 분석…은 프로젝트의 저장된 분석 결과(모든 브랜치의 최신 결과 · 활동 기록 · 스냅숏 · 새 코드 기준)를 지우고 곧바로 다시 분석합니다. 기준이 없어지므로 코드 전체가 새 코드가 되어, 새 코드만 보는 품질 게이트도 전체 문제를 기준으로 판정합니다. 결과만 삭제는 이슈 처리 상태(확인 · 오탐 · 담당자 · 주석)를 남기고, 처리 상태까지 모두 삭제는 그것도 지웁니다. 되돌릴 수 없습니다.

용어뜻
Ca (구심 결합)이 모듈을 가져다 쓰는(이 모듈에 의존하는) 다른 모듈의 수. 클수록 많은 곳이 기대고 있어 바꾸기 조심스럽습니다
Ce (원심 결합)이 모듈이 가져다 쓰는 다른 모듈의 수. 클수록 다른 모듈이 바뀔 때 영향을 받습니다
I (불안정도)I = Ce ÷ (Ca + Ce), 0~1. 0에 가까우면 안정, 1에 가까우면 불안정. 의존은 I가 작은 쪽으로 향하는 것이 좋습니다
순환 (순환 의존)모듈들이 서로를 거쳐 다시 자기 자신에게 돌아오는 의존(그래프의 빨간 선). 끊는 것이 좋습니다
모듈의존을 묶는 단위(가져오기 import/include 기준의 소스 폴더 · 패키지). 상자 테두리 색이 I입니다

모듈(폴더 · 패키지) 사이의 의존 그래프입니다. 색은 불안정도 I = Ce / (Ca + Ce)(안정 I = 0 ~ 불안정 I = 1), 빨간 선은 순환 의존입니다. 휠로 확대 · 축소, 끌어서 이동, 맞춤으로 전체 보기. 모듈을 누르면 파일 수 · Ca · Ce · I, 쓰는 모듈, 이 모듈을 쓰는 곳이 나옵니다. 아래 표에 모듈 · 의존 · 순환 목록과 아키텍처 이슈가 있습니다. 레이어 규칙은 관리 › 분석 설정에서 정합니다.

큰 프로젝트(이슈 수십만 개)도 다룰 수 있도록, 창에는 열린 프로젝트의 이슈만 올라옵니다. 프로젝트를 열거나 분석이 끝나면 이슈를 나눠 받으며, 그동안 화면 아래에 이슈 불러오는 중… n / 전체가 보입니다. 다른 프로젝트로 바꾸면 그 프로젝트의 이슈를 받고 앞 프로젝트의 이슈는 메모리에서 내립니다. 긴 목록은 페이지로 넘겨 봅니다(아래 줄의 처음 · 이전 · 페이지 번호 · 다음 · 끝, 페이지당 100 · 200 · 500 · 1000줄). 이슈가 많은 분석은 창에 가장 심각한 20만 개까지만 올리지만, 이슈 화면의 검색은 분석 전체에서 합니다: 검색어(규칙 · 메시지(한국어 · 영어) · 경로의 일부, 띄어 쓴 낱말은 모두 들어 있어야 함), 심각도 · 유형 · 상태 · 엔진 · 표준 · 새 코드만, 정렬(심각도 · 파일 · 규칙 · 새 코드 먼저 · 분석 순서)을 서버가 처리하고, 유형 탭의 건수와 페이지도 그 결과를 따릅니다. 이슈는 데이터 폴더의 로컬 데이터베이스(SQLite)에 프로젝트마다 폴더(projects/<프로젝트>/)를 두고 분석 · 스냅샷마다 파일 하나씩 저장되므로 수백만 개라도 한 페이지와 건수를 바로 읽고, 이슈의 처리 상태를 바꾸면 그 이슈만 저장합니다. 이전 버전의 이슈 파일(issues/*.ndjson)은 처음 열 때 데이터베이스로 옮겨집니다.

버그 · 취약점 · 코드 스멜 목록입니다. 위에서 검색(규칙, 메시지, 파일로 검색)하고 심각도(차단 · 심각 · 주요 · 경미 · 정보), 종류, 상태, 엔진, 표준(OWASP · CWE · MISRA · 행정안전부 등), 언어, 새 코드만으로 거릅니다. 보안 보고서 · MISRA 에서 범주를 눌러 오면 범주 필터가 걸리고 필터 해제로 풉니다.

이슈를 누르면 오른쪽 세부 정보 패널에 다음이 나옵니다.

  • 예외 신청 — 예외 신청과 승인

여러 이슈를 고르려면 선택을 눌러 체크한 뒤 선택 항목에 적용으로 상태 · 담당을 한 번에 바꿉니다. 여러 이슈를 한꺼번에 오탐이나 수용으로 바꿀 때는 "선택한 이슈 {n}개를 … 계속할까요?" 를 먼저 묻습니다. 처리 · 담당 · 태그 변경은 하나든 여럿이든 편집 › 실행 취소로 되돌립니다.

이슈 상태: 열림 · 확인됨 · 다시 열림 · 해결됨(고침 · 오탐 · 고치지 않음) · 수락함 · 닫힘. 다음 분석에서 같은 이슈(규칙 · 파일 · 줄 내용이 같음)가 다시 나오면 상태 · 의견 · 담당이 그대로 이어집니다.

결함 #

화면 위의 용어 설명: CID(결함 식별자 — 분석이 바뀌어도 같은 결함을 같은 번호로 추적, 스냅숏 비교의 기준), 영향(결함이 일으킬 수 있는 피해: 높음 · 보통 · 낮음), 체커(결함을 찾은 검사 규칙 이름, 예: NULL_RETURNS), 미해결(고치지도 기각하지도 않은 결함), 기각(오탐 또는 의도됨으로 분류한 결함), 스냅숏 · 스트림(커밋한 분석 한 번의 결함 목록, 브랜치별 스냅숏의 흐름).

정밀 결함 분석의 결함 목록입니다. 위의 보기 단추로 미해결 · 새로 발견 · 영향 높음 · 기각 · 수정됨을 고르고, CID, 체커, 파일, 함수로 검색합니다. 결함을 누르면 오른쪽에 체커 · 영향(높음 · 보통 · 낮음) · 컴포넌트 · 함수, 이벤트 경로(예: 할당 → 해제 → 사용, 메인 이벤트 강조), 그리고 분류(triage) 입력이 나옵니다.

항목값
분류Unclassified · Pending · Bug · False Positive · Intentional
조치Undecided · Fix Required · Fix Submitted · Modeling Required · Ignore

소유자 · 외부 참조 · 레거시담당자, 버그 추적 번호, 레거시 결함으로 표시

스트림 #

결함 커밋을 할 때마다 브랜치 이름의 스트림에 스냅샷이 쌓입니다. 스냅샷별 미해결 · 새로 발견 · 영향 높음 · 기각 · 수정됨과 정책 결과, 스냅숏 비교가 있습니다. 첫 스냅샷은 기준이고, 정책은 다음 커밋부터 새 결함을 셉니다.

컴포넌트 #

경로 패턴(glob)을 컴포넌트 이름과 소유자에 연결합니다(예: src/net/** → Network, 김철수). 맞지 않는 파일은 Other 입니다. 결함 목록과 보고서가 컴포넌트별로 묶입니다.

정책 #

기본 정책 "정밀 결함 분석 기본"은 기준 스냅샷 이후 새로 생긴 영향 높음 결함(보안 포함)이 하나라도 있으면 커밋을 실패로 둡니다. 이 프로젝트에 지정으로 프로젝트에 붙입니다. 정책이 실패하면 상태 표시줄에 "정밀 결함 분석 정책을 통과하지 못했습니다." 가 나오고 npm run defects -- commit-defects 는 종료 코드 1 을 냅니다.

함수 모델 #

라이브러리 함수의 동작을 알려 주어 결함을 더 찾습니다. 함수 이름 패턴과 종류(allocator 할당, sink 위험한 사용, source 외부 입력)를 적어 더합니다. npm run defects -- make-library 로 C 스텁에서 만들 수도 있습니다.

웹 스캔 (DAST) #

실행 중인 웹 애플리케이션을 HTTP 로 검사합니다. 직접 소유하거나 검사 권한을 받은 대상에만 쓰세요. 입력한 대상 출처 밖으로는 요청하지 않습니다.

  1. 대상 URL 을 적고 모드를 고릅니다. 수동 (관찰만) 은 페이지를 둘러보고 응답만 살핍니다. 능동 (안전한 탐침) 은 XSS · SQL 주입 같은 파괴적이지 않은 GET/POST 탐침을 더하며, 시작 전에 "권한이 있습니다" 확인을 받습니다.
  2. 필요하면 초당 요청(기본 5) · 최대 요청(기본 500) · 최대 페이지 · 최대 깊이, 인증 · 시드(쿠키, Bearer 토큰, 추가 헤더, 로그인 URL · 로그인 필드, 시드 URL, OpenAPI / Swagger)를 정합니다.
  3. 검사 시작 — 진행(단계 · 요청 · 페이지 · 발견)이 나오고 취소로 멈춥니다.
  4. 검사 기록에서 결과를 고르면 발견 목록이 나오고, 발견을 누르면 매개변수 · 증거 · 요청 · 응답이 나옵니다. SARIF 저장으로 내보냅니다.

권한 검사가 켜져 있으면 검사 결과는 분석 실행 권한이 있는 사용자도 읽을 수 있습니다. 예약 분석으로 능동 검사를 예약할 때도 같은 "권한이 있습니다" 확인을 받습니다.

품질 프로파일 #

언어마다 어떤 규칙을 켤지 정합니다. 처음에는 언어마다 기본 프로파일 "Checker way" 가 있습니다.

  • 복사 · 상속해 만들기(부모 프로필의 설정을 물려받고 차이만 저장, "부모에서 꺼짐" 표시) · 기본값으로 · 이 프로젝트에 사용

  • 비교 탭 — 비교할 프로필과 규칙 차이
  • 변경 기록 탭 — 만듦 · 켬 · 끔 · 심각도 · 부모 변경 · 복원, 변경한 사람과 시각
  • 백업 · 복원 — 프로파일을 JSON 으로 저장하고 되살립니다

기본 프로필이나 하위 프로필이 있는 프로필은 지울 수 없습니다.

사용자 규칙(도구 › 사용자 규칙)은 정규식 규칙입니다: 정규식 · 이름 · 종류 · 심각도를 정하면 다음 분석부터 맞는 줄마다 이슈가 됩니다.

품질 게이트 #

품질 게이트는 언제나 현재 상태를 알려 줍니다. 기본 게이트는 코드 전체의 버그 · 취약점 수, 핫스팟 검토율, 커버리지, 중복률, 신뢰성 · 보안 · 유지보수성 등급으로 판정하고(직전 분석 이후 바뀐 코드만 보지 않음), 이슈를 오탐 · 수락으로 처리하거나 게이트 조건을 바꾸면 다시 분석하지 않아도 곧바로 다시 판정합니다. 새 코드만 보려면 조건의 측정값을 새 코드 · … 로 고르세요. 조건은 설정 › 품질 게이트에서 켜고 끄거나 임계값을 바꿉니다. 꺼진 조건은 "꺼짐"으로 보이고 판정하지 않습니다.

분석이 통과인지 실패인지 가르는 조건 목록입니다. 기본 게이트 "Checker way" 의 조건(모두 새 코드 기준):

측정값연산자임계값
새 버그 · 새 취약점>0
검토한 새 보안 핫스팟<100 %
새 코드 커버리지<80 %
새 코드 중복>3 %
새 코드 유지보수성 · 신뢰성 · 보안 등급나쁨A

복사본 추가로 새 게이트를 만들고 조건 추가로 측정값 · 연산자 · 임계값을 정한 뒤 {name} 프로젝트에 지정합니다. "이 프로젝트에 사용 중" 이 지금 쓰는 게이트입니다.

포트폴리오 #

여러 프로젝트를 묶어 함께 봅니다. 이름을 적고 포트폴리오 만들기, 프로젝트 고르기로 구성원을 정합니다. 통과 · 실패 · 없음 수, 가장 나쁜 프로젝트 기준 등급, 합친 측정값, 출시 가능 판정(실패한 프로젝트가 없으면 통과)이 나옵니다.

백그라운드 작업 #

모든 분석이 작업으로 남습니다(최근 100개): 시각, 프로젝트, 브랜치, 상태(SUCCESS · FAILED · CANCELED — 진행 창에서 취소한 분석), 품질 게이트, 정밀 결함 분석 정책, 걸린 시간, 경고(예: DB: …). CI 스캐너나 API 로 보낸 분석도 여기 나옵니다.

분석 설정 #
  • 새 코드 기준 — 이전 분석 · 일수 · SCM 변경 줄 (git) · 이전 버전 이후(버전 태그) · 특정 분석 이후. 기준 참조 (브랜치·태그·커밋), 적용 범위: 이 프로젝트에만 적용을 켜면 이 프로젝트만 다른 기준을 씁니다.
  • 자동 담당자 — git blame 작성자에게 이슈 배정.
  • 예외 승인 — 오탐·수용 처리에 승인 필요, 신청자 본인 승인 허용.
  • 라이선스 정책 — 허용 · 검토 · 금지할 SPDX ID(줄마다). 적지 않은 라이선스는 범주 기본값(허용형 허용, 카피레프트 검토, 네트워크 카피레프트 · 독점 금지). 내부 패키지(의존성 혼동 검사, glob 또는 /정규식/).
  • C/C++ 설정 — 대상 데이터 모델(LP64 · ILP32 · LLP64), 포함 디렉터리, 매크로 정의(NAME 또는 NAME=값).
  • 커버리지 보고서 — 보고서 경로(프로젝트 기준, 줄마다). 비우면 coverage/lcov.info, cobertura.xml, jacoco.xml, clover.xml, opencover.xml 같은 흔한 위치를 찾습니다.
  • 아키텍처 규칙 — 레이어(이름 + 경로 패턴), 금지 의존(이 레이어가 → 이 레이어를 쓰면 안 됨, 설명), 모듈당 최대 의존 수, 불안정 의존 알림. 프로젝트 관리자만 바꿉니다.
  • 정리 (하우스키핑) — 쓰지 않은 브랜치 · 닫힌 이슈 상태 · 감사 로그 보관 일수(0 = 끔), 지금 정리. 지우기 전에 무엇을 지울지(예: "30일 지난 감사 기록") 보여 주고 확인을 받습니다.

예약 분석 #

새 예약 → 이름(예: 야간 전체 분석) · 종류(코드 분석 / 웹 스캔 (DAST)) · 프로젝트(또는 프로젝트 대신 폴더 경로) · 브랜치, DAST 면 대상과 스캔 방식 · 실행 시각(매일 02:00 · 평일 09:00 · 매주 일요일 03:00 · 매시간 정각 · 사용자 지정 (cron)) · 예약 사용. cron 식은 "분 시 일 월 요일" 순서입니다(예: */30 8-18 * * 1-5 는 평일 8시~18시 30분마다). 다음 실행 5회로 미리 확인합니다. 목록에서 다음 실행 · 마지막 실행 · 결과를 보고 지금 실행, 편집, 삭제를 합니다. 예약은 프로그램(또는 웹 서버)이 켜져 있을 때 30초마다 확인해 실행합니다. 웹 스캔을 능동 방식으로 예약하면 웹 스캔 화면과 같은 "권한이 있습니다" 확인을 받습니다.

연동 #
  • 기본 URL — 메일과 티켓에 넣을 이 서버의 주소.
  • SMTP — 호스트 · 포트 · 보안 연결(암호화 안 함 · STARTTLS · TLS) · 사용자 · 비밀번호 · 보내는 주소, 연결 확인, 테스트 메일(받는 주소).
  • LDAP — LDAP 주소 · 바인드 DN · 비밀번호 · 검색 기준 DN · 사용자 필터 · 기본 그룹 · 그룹 대응(JSON, LDAP 그룹 → 로컬 그룹), 연결 확인. 켜면 회사 디렉터리 계정으로 로그인합니다.
  • 이슈 트래커 — Jira(기본 URL · API 버전 · 프로젝트 키 · 이슈 유형 · 이메일 + API 토큰 또는 개인 액세스 토큰 (PAT)), Redmine(기본 URL · API 키 · 프로젝트 ID · 트래커 ID), GitHub(API 주소 · 소유자 · 저장소 · 토큰), GitLab(기본 URL · 프로젝트 ID · 토큰). 쓰지 않는 칸은 비워 둡니다.
  • PR 게시 (ALM) — GitHub · GitLab · Azure DevOps(조직 · 프로젝트 · 저장소 ID · 토큰) · Bitbucket(종류 Cloud / Server, API 주소 또는 기본 URL, 워크스페이스 또는 프로젝트 키 · 저장소 · 토큰).
  • 내 알림 — 받을 이메일, 알릴 일(품질 게이트 상태가 바뀜 · 나에게 이슈가 할당됨 · 영향 높은 결함이 새로 나옴 · 승인할 예외 신청이 들어옴 · 내 예외 신청이 승인됨 · 반려됨 · 분석이 실패함), 프로젝트(아무것도 고르지 않으면 모두). 알림 저장 / 알림 끄기.

비밀 값(비밀번호 · 토큰 · 키)은 저장 뒤 다시 보이지 않습니다("저장된 값이 있습니다. 바꾸려면 새 값을 적으세요.").

사용자와 권한 #

처음에는 권한 검사가 꺼져 있습니다 (로컬 단일 사용자). 여러 사람이 쓰는 서버라면:

  1. admin 사용자의 비밀번호(8자 이상)를 먼저 정합니다.

  2. 권한 검사를 켭니다. 켜기 전에 로그인할 관리자 계정 이름을 보여 주고 확인을 받습니다(비밀번호가 있는 활성 관리자가 없으면 켜지지 않음). 이때부터 화면은 MyCodeChecker 로그인 창을 띄우고, API 는 로그인이나 토큰을 요구합니다. 로그인 창에도 언어 선택이 있고, 고른 언어는 로그인한 뒤에도 그대로입니다.

  3. 사용자 추가(로그인 · 이름 · 이메일 · 비밀번호), 그룹 추가(기본 그룹 administrators · users), 구성원 추가.

  4. 전역 권한: 관리 · 품질 게이트 관리 · 품질 프로파일 관리 · 분석 실행 · 프로젝트 만들기. 프로젝트 권한: 보기 · 소스 보기 · 이슈 관리 · 보안 핫스팟 관리 · 관리 · 분석 실행. 권한 주기로 사용자나 그룹(받는 쪽)에 줍니다.

  5. 토큰 — 토큰 만들기: 사용자 토큰(mcu_…, 그 사용자의 권한), 프로젝트 분석 토큰(mcp_…, 그 프로젝트 분석만), 전역 분석 토큰(mca_…, 모든 분석). 이 토큰은 지금 한 번만 보입니다. 토큰 창의 이 토큰으로 분석 결과 올리기에는 그대로 복사해 쓸 명령 예와 mcc-project.properties 예가 있습니다.

    node scripts/scan.mjs --path <소스 폴더> --server <서버 URL> --token <토큰> --project-key <키>

    데스크톱 앱의 내장 서버는 실행할 때마다 임의 포트를 쓰므로, CI 에서 올리려면 공유 서버(npm run web:serve 또는 웹판)가 필요합니다. 만든 날 · 마지막 사용을 보고 폐기합니다.

비활성화한 사용자는 로그인할 수 없습니다. 로그아웃은 도구 › 로그아웃.

안전 장치 — 실수로 잠기거나 지우지 않도록 다음을 지킵니다.

  • 마지막 활성 관리자는 지우거나 비활성화할 수 없습니다(LAST_ADMIN).
  • 사용자 · 그룹 · 게이트 · 프로파일 · 포트폴리오 · 정책 · 컴포넌트 · 모델 삭제, 사용자 비활성화, 토큰 폐기, 여러 이슈의 일괄 오탐 · 수용, 정리(하우스키핑) 전에는 확인 창이 나옵니다.
  • 같은 로그인으로 5번 잘못 로그인하면 그 계정은 5분 동안 잠깁니다("로그인에 여러 번 실패했습니다. 몇 분 뒤에 다시 시도하십시오.").

설정 #

도구 › 설정(Ctrl+,)은 크기가 정해진 창(920×600)이며, 왼쪽에 세로 탭이 있습니다. 바꾼 값은 초안이고 확인을 눌러야 저장됩니다(바뀐 탭에는 "바뀜" 표시). 취소(Esc)는 저장하지 않고 닫고, 확인(Enter, 여러 줄 입력 칸 밖에서)은 저장하고 닫습니다. 초기화는 지금 탭만 기본값으로 되돌립니다(확인을 누르기 전에는 저장되지 않음). 테마 · 언어 · 시작 화면 배경은 바로 미리 보이고, 취소하면 되돌아갑니다.

이슈 분류 (triage) #

  1. 개요에서 실패한 게이트 조건이나 등급 카드를 눌러 이슈 목록으로 갑니다. 새 코드만을 켜면 이번 변경에서 생긴 것만 봅니다.
  2. 심각도 · 종류로 걸러 위에서부터 봅니다. 이슈마다 이유 · 고치는 법을 읽고:
    • 맞으면 확인됨, 담당을 정하고 필요하면 티켓 만들기
    • 잘못 찾았으면 오탐, 알지만 지금 안 고칠 것이면 수용(승인이 필요한 작업 공간이면 예외 신청)
  3. C/C++ 결함은 결함 보기에서 이벤트 경로를 따라가 분류 · 조치를 정합니다.
  4. 보안 핫스팟은 보안 핫스팟 보기에서 안전 · 고침 · 인지함으로 검토합니다.
  5. 고친 뒤 다시 분석하면 사라진 이슈는 닫힘(고침)이 됩니다.

예외 신청과 승인 #

  1. 관리자가 관리 › 분석 설정 › 예외 승인 › 오탐·수용 처리에 승인 필요를 켭니다(본인 승인을 막으려면 신청자 본인 승인 허용을 끔).
  2. 개발자는 이슈 패널의 예외 신청에서 예외 종류(오탐 / 수용)와 예외 사유(필수)를 적고 예외 신청을 누릅니다. 이슈에 "승인 대기" 가 붙고, 알림을 구독한 승인자에게 메일이 갑니다.
  3. 승인자(이슈 관리 권한)는 예외 승인 보기에서 신청을 고르고 처리 의견과 함께 승인 또는 반려(의견 필수)합니다. 승인하면 이슈가 오탐/수용으로 해결되고, 반려하면 열린 채로 남으며 신청자에게 알림이 갑니다.
  4. 신청자는 승인 전에 신청 취소할 수 있습니다. 모든 신청 · 결정은 이슈의 변경 기록과 감사 로그에 남습니다.

CI 의 품질 게이트 #

빌드 서버에서 소스를 바로 분석하고 게이트가 실패하면 빌드를 멈춥니다.

node scripts/scan.mjs --path . --format sarif --out mcc.sarif
# 종료 코드: 0 통과, 1 게이트 실패(또는 --misra-gate 미준수), 2 사용법 오류

GitHub Actions 예:

- run: npm ci
- run: node scripts/scan.mjs --path . --coverage coverage/lcov.info --format sarif --out mcc.sarif
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with: { sarif_file: mcc.sarif }

--standard misra-c|misra-cpp|cert|cwe-top25|owasp 는 그 표준의 규칙만 켜고, --report misra --out misra.pdf 는 보고서 파일을 만듭니다(--report 와 함께 --out 이 .pdf · .docx · .xlsx 로 끝나면 그 형식). --exclude <glob> 은 맞는 파일을 빼며 여러 번 쓸 수 있고 mcc.exclusions 와 합쳐집니다.

--workspace [설정 폴더] 를 주면 앱의 작업 공간(기본은 앱 데이터 폴더)에 있는 품질 프로파일 · 품질 게이트 · 제외 패턴 · 이슈 상태(오탐 · 수용 처리 등)로 분석해 화면과 같은 결과를 냅니다. 분석은 작업 공간의 임시 사본에서 돌므로 작업 공간은 바뀌지 않습니다.

node scripts/scan.mjs --path . --workspace --exclude "**/generated/**" --report executive --out summary.docx

결과를 서버에 쌓으려면 아래 "서버로 올리기" 를 씁니다.

서버로 올리기 #

팀 서버(웹판)에 분석을 쌓으면 서버의 프로파일 · 게이트 · 이슈 상태 · 기록이 적용됩니다(코드 품질 스캐너 방식).

  1. 서버에서 관리 › 사용자 · 권한 › 토큰으로 프로젝트 분석 토큰을 만듭니다(새 프로젝트면 프로젝트 만들기 권한이 있는 사용자 토큰).

  2. 프로젝트 루트에 mcc-project.properties 를 둡니다.

    mcc.host.url=https://checker.example.com
mcc.projectKey=my-app
mcc.projectName=My App
mcc.sources=src
mcc.exclusions=**/generated/**

  3. CI 에서 MCC_TOKEN(호환 형식의 환경 변수도 읽음)을 비밀 값으로 두고 node scripts/scan.mjs --branch $BRANCH 를 실행합니다. 파일을 올리고 서버의 게이트 결과를 기다려, 실패하면 종료 코드 1 과 실패한 조건을 출력합니다.

데스크톱 앱의 내장 서버는 실행할 때마다 임의 포트를 쓰므로 CI 가 올릴 곳으로 쓸 수 없습니다. 공유 서버(npm run web:serve 또는 node server/server.js --host 0.0.0.0 --port 5211)를 띄웁니다. 토큰을 만들 때 나오는 명령 예를 그대로 써도 됩니다.

mcc.modules=a,b 를 쓰면 모듈마다 따로 프로젝트로 올립니다(a.mcc.projectKey …). 서버는 /api/qualitygates/project_status, /api/issues/search 같은 호환 Web API 도 제공합니다.

npm run defects -- format-errors --dir .mcc --html-output cov-html --json-output-v8 defects.json
npm run defects -- commit-defects --path . --stream main --token mcp_…
npm run defects -- manage-im --mode defects --update --cid 12 --set classification:"False Positive"

build 는 --compile-commands compile_commands.json 도 받습니다. analyze 의 --enable · --disable · --disable-default 로 체커를 고르고, --coding-standard-config 로 misra-c2012 · misra-cpp2023 · cert-c · autosar · misra-c2004 · misra-cpp2008 · mois(행정안전부)를 켭니다. commit-defects 는 스트림에 스냅샷을 남기고 정책이 실패하면 종료 코드 1 입니다. 개발자 PC 에서는 run-desktop 이 스트림을 바꾸지 않고 스트림에 없는 새 결함만 보여 줍니다(도구 모음의 데스크톱과 같음).

풀 리퀘스트 분석 #

보기 › 풀 리퀘스트 분석(git 필요). 대상 브랜치와 PR 번호를 정하고 PR 분석을 누르면 대상과 비교해 바뀐 줄의 이슈만 봅니다. 기준 커밋, 바뀐 파일 · 줄 수, PR 게이트(기본 게이트의 새 코드 조건), "커밋 안 한 변경 있음" 경고가 나옵니다. Markdown 요약과 코드 호스트별 장식 페이로드(GitHub Checks, GitLab Code Quality, Azure DevOps 스레드, Bitbucket Code Insights)를 복사할 수 있고, 관리 › 연동의 ALM 연결이 있으면 PR에 결과 게시(PR 번호 / MR IID / PR ID, 헤드 커밋 SHA)로 바로 올립니다.

보고서 만들기 #

파일 › 보고서… 또는 보고서 보기. DB 를 설정했으면 여기의 DB로 내보내기로 지금 분석을 DB 에 저장합니다.

  1. 보고서 종류: 경영진 요약 · 보안 보고서 · MISRA 준수 보고서 · 정밀 결함 분석 무결성 보고서 · 정밀 결함 분석 보안 보고서 · 규칙 집합 준수 (보안 약점 점검) · SBOM 보고서. 보안 보고서는 표준, 보안 약점 점검 보고서는 규칙 집합(모든 규칙 · 보안 규칙 · CWE 규칙 · CWE Top 25 · OWASP Top 10 2021 · CERT C/C++ · MISRA C:2012 · C:2023 · C++:2023)을 고릅니다.
  2. 미리 보기를 확인하고 HTML 저장 · CSV 저장 · 파일로 내려받기(Word · Excel · PDF) · 인쇄를 합니다. 보고서는 고른 언어(한국어 / English)로 만들어집니다.
  3. 규제 보고서 (ZIP) 는 경영 · 보안 · 무결성 · 규칙 세트 · SBOM 보고서 PDF 와 이슈 목록 Excel 을 ZIP 하나로 묶습니다(감사 · 납품용). 규정 제출 묶음에서 기준(한국 행정안전부 SW 보안약점 49 (2021) · 주요정보통신기반시설 웹)과 넣을 보고서 종류를 고릅니다. 하나도 고르지 않으면 만들 수 없습니다.

빠른 내보내기는 파일 메뉴의 JSON · SARIF · HTML · CSV · 품질 게이트 배지(SVG) · 결함 CSV 입니다. 데스크톱에서는 내보내기마다 저장 창으로 위치와 이름을 고르고, 저장하면 저장됨: <경로> 가 나옵니다. 웹판은 브라우저 내려받기로 저장합니다.

AI 코드 수정 #

  1. 설정 › AI 코드 수정에서 AI 코드 수정 사용을 켜고 제공자 · 모델을 정한 뒤 연결 확인을 하고 확인으로 저장합니다(관리 권한 필요).
  2. 이슈를 고르고 세부 정보 패널의 AI 코드 수정에서 AI로 수정 제안을 누릅니다("AI가 수정안을 만드는 중…"). 변경 내용(지울 줄 · 넣을 줄), 설명, 확신(high · medium · low), 사용한 토큰 (입력 / 출력)이 나옵니다. 모델이 오탐이라고 보거나 안전하게 고칠 수 없으면 "자동 수정 없음 (설명만)" 으로 이유만 보여 줍니다. 마음에 들지 않으면 다시 요청합니다. 기능이 꺼져 있으면 "AI 코드 수정이 꺼져 있습니다." 와 설정 열기가 나옵니다.
  3. 수정안을 읽고 맞으면 적용을 누릅니다(이슈 관리 권한 필요). 제안을 만든 뒤 파일이 바뀌었으면 적용을 거절하고 "파일이 바뀌었습니다. 다시 요청하세요." 를 보여 줍니다. 적용하면 "{파일}: n줄 지우고 m줄 넣었습니다." 가 나오고, 다시 분석으로 이슈가 사라졌는지 확인합니다.
  4. 적용한 수정이 마음에 들지 않으면 되돌리기(또는 편집 › 실행 취소)를 누릅니다. 적용 전 원본을 따로 보관해 두었다가 파일을 그대로 되돌립니다. 적용한 뒤 파일을 또 고쳤으면 "수정을 적용한 뒤 파일이 바뀌어 자동으로 되돌릴 수 없습니다." 로 거절합니다.

적용은 소스 파일을 직접 고칩니다. 버전 관리(git)로 바뀐 내용을 검토하고 커밋하세요. AI 수정안은 틀릴 수 있습니다.
